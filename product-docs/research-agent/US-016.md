# US-016: Backlog Integration – Productboard (Product Management)

## Metadata
- **Repo**: `Product-OS-Research-Agent`
- **ID**: US-016
- **Status**: `create`
- **Branch**: (not yet created)
- **Dependencies**: US-003 (integration service), US-007 (entity/field mapping pattern). Productboard features, ideas, notes, roadmap align naturally with Product OS feature_request, roadmap_item, prd.

## Target Users
- **Primary**: Admins configuring Productboard as a data source for Product OS.
- **Secondary**: PMs searching features, ideas, and roadmap in Research Agent with evidence and citations to Productboard.

## Goal

Deliver a **dedicated Productboard integration** so Product OS can connect to Productboard, map features, ideas, notes, and roadmap entities to canonical Product OS entity types, and sync them into the Research Agent for search and evidence in chat.

## Problem Statement

Productboard is a central tool for features, ideas, feedback, and roadmap. Without an integration, that data is siloed from the Research Agent. This integration must support Productboard auth (API token or OAuth2), entity selection (features, ideas, notes, components, roadmap), and field mapping to Product OS so PMs can ask questions and get answers grounded in Productboard data with citations.

## Technical Context (Research Summary)

- **Auth**: (1) API token in header (`Authorization: Bearer <token>`) or as `access_token` query param. Token from Productboard API settings. (2) OAuth2 for third-party apps: user auth flow, admin approval, registration at `app.productboard.com/oauth2/applications`; recommended for production. API v2 (Dec 2025) adds 8 OAuth scopes for granular permissions.
- **API**: Productboard Public API v2. Base URL and docs: developer.productboard.com.
  - **Entities**: Features, initiatives, other entity types; list/create with filtering by type. Entity relationships: parent, child, link, isBlockedBy, isBlocking.
  - **Notes**: Owner and createdBy use membership UUIDs.
  - **Teams / Members**: List workspace members, teams, team members (APIs publicly available).
- **Entity mapping**: Productboard features → Product OS feature_request or roadmap_item; ideas → feature_request; notes → meeting_note or generic note entity; roadmap items → roadmap_item. Components and initiatives can map to Product OS entities or hierarchy (epic/feature). Field mapping: Productboard fields → canonical title, description, status, priority, etc.

## Non-Goals

- Writing back to Productboard (e.g. pushing status from Product OS) in this story; read/sync only for MVP.
- Full Productboard UI parity; integration is for ingestion and search only.

## Acceptance Criteria

*(To be refined in Phase 2.)*

- **AC1 – Connect**  
  Admin can connect Productboard in Product OS via API token or OAuth2. Credentials stored securely; connection status visible in UI.

- **AC2 – Select scope**  
  Admin can choose which Productboard entity types to sync (features, ideas, notes, roadmap, components/initiatives as applicable). Optional filters (e.g. status, product) persisted and used by sync.

- **AC3 – Entity and field mapping**  
  Admin can map Productboard entity types to Product OS entity types (feature_request, roadmap_item, prd, meeting_note, etc.). Mapping follows US-007 pattern: entity type → Productboard type, then field mapping.

- **AC4 – Field mapping**  
  For each entity type, admin can map Productboard fields to canonical Product OS fields (title, description, status, priority, etc.). Required canonical fields must be mappable.

- **AC5 – Sync and ingestion**  
  Sync job fetches selected Productboard entities (with pagination and relationship handling where needed), normalizes to canonical entities + entity_fields + chunks, and ingests into Research Agent store and vector index. Incremental sync by updated date when API supports it.

- **AC6 – Search and citations**  
  Ingested Productboard data appears in `list_sources` and `search_memories` with correct entity_type and citations to Productboard (feature/idea/note URLs).

- **AC7 – NFRs**  
  Credentials stored server-side only; use minimal OAuth scopes when using OAuth2. No secrets in frontend or logs; clear errors for invalid/expired token or scope issues.

## NFRs / Constraints

- Productboard API rate limits and pagination must be respected. Entity relationships (parent/child, links) can be stored as metadata or separate fields for richer search if needed.
