# US-013: Backlog Integration – Mixpanel (Product Analytics)

## Metadata
- **Repo**: `Product-OS-Research-Agent`
- **ID**: US-013
- **Status**: `create`
- **Branch**: (not yet created)
- **Dependencies**: US-003 (integration service), US-007 (mapping pattern where applicable). Mixpanel is analytics-backed; entity model may extend to “product_usage” or “analytics_insight” for evidence in research.

## Target Users
- **Primary**: Admins configuring Mixpanel as a data source for Product OS.
- **Secondary**: PMs using product usage and funnel/retention data as evidence in Research Agent (e.g. “what features are used most?”, “where do users drop off?”).

## Goal

Deliver a **dedicated Mixpanel integration** so Product OS can connect to Mixpanel, configure which events and (optionally) profiles or report outputs to sync, and expose product usage and analytics-derived insights as first-class evidence in Research Agent search and chat.

## Problem Statement

Product decisions should be grounded in usage data. Mixpanel holds events, funnels, retention, and profiles. Without an integration, PMs cannot combine Mixpanel evidence with backlog, support, and PRDs in one place. This integration must support secure auth, configurable event/export scope, and mapping of Mixpanel data into Product OS entities (or a dedicated analytics entity type) so the Research Agent can cite usage and trends.

## Technical Context (Research Summary)

- **Auth**: Basic auth with project token in header. Token from Mixpanel project settings. No OAuth for raw export; Data Pipelines (BigQuery, etc.) are a separate add-on.
- **APIs**:
  - **Raw Event Export**: `GET https://data.mixpanel.com/api/2.0/export` (or `data-eu.mixpanel.com`, `data-in.mixpanel.com` for EU/IN). Query params: `from_date`, `to_date` (YYYY-MM-DD, UTC for newer projects), `event` (optional filter), `limit` (max 100,000). Returns JSONL. Rate limits: 60/hour, 3/sec, 100 concurrent.
  - **Query API**: Insights, Funnels, Retention, JQL (paid). Exports formatted report results.
  - **Engage (Profiles) API**: User/group profile export as JSON.
- **Entity mapping**: Events are not “backlog” items; they are evidence. Options: (1) Ingest event names + properties as searchable “product_usage” or “analytics_event” entities with fields (event_name, properties, date, counts); (2) Ingest pre-aggregated report outputs (e.g. funnel steps, retention table) as “analytics_insight” entities. Configurable date range and event filter per connection.

## Non-Goals

- Full JQL or Data Pipelines implementation in this story (raw export + optional report snapshot is sufficient for MVP).
- Real-time streaming; batch/scheduled export only.
- Editing or writing data back to Mixpanel.

## Acceptance Criteria

*(To be refined in Phase 2.)*

- **AC1 – Connect**  
  Admin can connect Mixpanel in Product OS (project token, optional region). Credentials stored securely; connection status visible in UI.

- **AC2 – Configure export scope**  
  Admin can set date range (e.g. last 30/90 days), optional event name filter, and optionally choose to sync aggregated insights (e.g. top events summary) vs raw event samples. Configuration persisted and used by sync.

- **AC3 – Entity and field mapping**  
  Admin can map Mixpanel data to Product OS entity type(s): e.g. “product_usage” or “analytics_event” with canonical-like fields (title/event_name, description/summary, properties, date, source_system=mixpanel). If canonical model is extended for analytics, mapping follows US-007 style.

- **AC4 – Sync and ingestion**  
  Sync job exports from Mixpanel within configured scope, normalizes to entities + chunks, and ingests into Research Agent store and vector index. Rate limits respected; pagination/sampling when limit applies.

- **AC5 – Search and citations**  
  Ingested Mixpanel data appears in `list_sources` and `search_memories` so PMs can ask usage-related questions and get answers with citations to Mixpanel (e.g. event names, date ranges, project).

- **AC6 – NFRs**  
  Token stored server-side only; no secrets in frontend or logs. Clear errors for invalid token or rate-limit exhaustion.

---

## NFRs / Constraints

- Respect Mixpanel rate limits; implement backoff and optional sampling for large ranges.
- Large exports (e.g. 100k events) may require chunked or summarized ingestion to avoid overload; define strategy in refinement.
