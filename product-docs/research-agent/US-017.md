# US-017: Integration Framework – Unified Onboarding and Integration Settings

## Metadata
- **Repo**: `Product-OS-Research-Agent`
- **ID**: US-017
- **Status**: `approved`
- **Branch**: (not yet created)
- **Dependencies**: US-003 (Monday integration), US-007 (entity/field mapping pattern), US-009 (Integrations View/Edit), US-011 (onboarding), US-012 (Jira integration)

## Target Users
- **Primary**: Product Managers and admins configuring integrations (adding or editing Monday, Jira, or future sources).
- **Secondary**: IT / admin users who maintain integrations and ensure the Research Agent has the right entities and field mappings.

## Goal

Provide a single **integration framework** (backend API surface + shared UX) so that every integration (Monday, Jira, and future ones) follows the same 5-step flow in both onboarding and integration settings, and new integrations can be added with minimal duplication and consistent, testable behavior.

By providing this framework, admins can add new integrations with minimal duplication and consistent UX, so that onboarding and settings stay aligned and new integrations (e.g. Mixpanel) are quick to ship and verify.

## Problem Statement

Monday and Jira each provide a different experience within either onboarding or integration settings; the API and UI are implemented per integration with duplicated routes and models. Adding Mixpanel, Gong, SharePoint, Productboard (US-013–US-016) would repeat this pattern. There is no shared "integration adapter" contract or reusable UI components, so UX and behavior drift and adding/testing new integrations is costly.

## Unified UX Pattern (to encode in framework)

1. **Select Product OS entities** – Which canonical types to sync (e.g. roadmap_item, feature_request, bug, task).
2. **Authenticate** – OAuth, API key, or other; connection status visible.
3. **Select source entity types** – e.g. Board, Epic, Bug, Story (Monday boards; Jira issue types).
4. **Field mapping** – Map source fields to Product OS canonical fields; **searchable dropdown** (Jira-style) for field selection.
5. **Sync** – Test sync then activate; only then does the integration participate in scheduled sync.

## Success Metrics

- Adding a net-new integration (e.g. Mixpanel) requires implementing only a defined adapter interface + UI registration, not new route trees or new wizard flows.
- Onboarding and Integration settings use the same 5-step flow and shared components for every supported integration.
- Contract tests (per integrations architect) verify adapter behavior without hitting live APIs.

## Non-Goals

- Rewriting Monday/Jira connectors from scratch (framework allows incremental migration).
- Confluence, Jira Data Center, or other out-of-scope products.
- Full two-way sync semantics in the framework (direction remains per-integration where needed).

## Scope Assumptions

- **UI ownership**: Integration settings and onboarding UI are implemented in or co-deployed with the Research Agent product (same repo or same release).
- **Migration**: US-017 includes migrating Monday and Jira to the new framework so that both use the unified adapter contract and shared UX; "done" means framework exists and both existing integrations run on it.
- **Research first**: A research/design phase produces a framework design doc (adapter interface, route strategy, shared config model, UI component contract); implementation follows that doc.

- **Adapter vs connector**: The framework **adapter** is the contract for the API/UI layer (config, schema, test, prepare, auth). The existing **BaseConnector** (or equivalent) remains the contract for sync/ingestion (e.g. list_updated_items, normalize_item). The design doc will define how they are wired (e.g. how config from the adapter is passed to the connector factory).

- **Sync model**: The framework assumes **pull/sync** (polling) by default for reliability; webhooks or push can be added per integration later if supported.

## Acceptance Criteria

- **AC1 – Integration adapter interface (backend)**  
  A single integration adapter interface (or abstract class) defines: get_config, upsert_config, get_schema, test_connection, prepare_sync, and optional auth hooks (e.g. OAuth authorize/callback). Monday and Jira each implement this interface; the server dispatches to the adapter by source_id. Existing route paths (e.g. /integrations/monday) may be retained for backward compatibility but must delegate to the adapter. The adapter is the API/UI contract; the existing BaseConnector (or equivalent) remains the sync/ingestion contract; the design doc defines how they are wired.

- **AC2 – Unified config and mapping model**  
  One generic config/mapping model (e.g. IntegrationConfig and EntityMappingConfig with a source discriminator) is used by the API for all integrations. New integrations do not introduce new response/request types for config or entity mapping; they use the same shapes with source-specific fields where needed.

- **AC3 – Registry and auth abstraction**  
  A registry of integration adapters by source_id exists. Auth (OAuth vs API key) is abstracted so the UI and backend call one contract; Jira OAuth and Monday API key are two implementations of that contract.

- **AC4 – One wizard flow (frontend)**  
  A single wizard flow for "add/edit integration" is used in both onboarding and integration settings. Steps: Select Product OS entities → Authenticate → Select source entity types → Field mapping (searchable dropdown) → Test & Sync. Per-integration pluggable pieces: auth component (OAuth redirect vs API key form), schema/options loader (boards vs projects/issue types).

- **AC5 – Shared field-mapping UX**  
  Field mapping uses a shared component: searchable dropdown for selecting source fields (Jira-style). Monday and all other integrations use this component; no integration-specific field-selector UI.

- **AC6 – New-integration checklist**  
  Documented checklist for adding a new integration: implement adapter (config, schema, test, prepare, auth if needed), register in backend registry, add to UI integration list and wizard (auth + schema steps). The checklist (and framework design doc) must require that connectors (sync layer) populate Entity with `source_id` and `source_system` (or equivalent) for traceability. A new integration (e.g. Mixpanel) can be added by following the checklist without adding new route trees or new wizard flows.

- **AC7 – Contract tests**  
  Contract tests (using mocks of external APIs) exist for the adapter interface. Each registered adapter has at least one contract test that verifies config, schema, test, and prepare behavior without hitting live third-party APIs.

- **AC8 – Monday and Jira on framework**  
  Monday and Jira are migrated to the new framework. Both use the adapter interface, shared config model, and shared wizard/field-mapping UX; existing behavior (connect, map, sync, test) is preserved.

## NFRs / Constraints

- **Backward compatibility**: Existing stored config for Monday and Jira continues to work after migration; no one-time data migration that drops or rewrites config without a clear upgrade path.
- **Performance**: get_schema and test_connection complete within 5s for typical scope (e.g. ≤50 boards or projects), or the API returns a timeout/error and the UI shows a loading or error state.
- **Security**: Auth credentials (tokens, API keys) remain stored only in backend config storage; adapter interface does not expose them to the client beyond "connected" status.
- **Discoverability**: The list of available integrations (and their auth type) is derivable from the registry so the UI can render "Add integration" and the correct auth step without hardcoding integration names.

- **Empty states**: When no integrations are registered, or get_schema returns no items (e.g. no boards, no projects), the UI shows an appropriate empty state and CTA (e.g. "Add your first integration", "No boards found—check permissions or try another account") rather than failing silently.

- **Traceability**: Connectors (sync layer) must populate Entity with `source_id` and `source_system` (or equivalent) for traceability; the framework design doc and new-integration checklist reference this requirement.

---

## Edge Cases & Error Handling

- **Auth or connection failure**: When test_connection or get_schema fails (invalid/expired token, network error), the adapter surfaces a structured error to the API; the UI shows a clear message and, for auth failures, a CTA to re-authenticate or update credentials. Mapping cannot be activated until connection succeeds.

- **Empty schema**: When get_schema returns no boards/projects/issue types, the UI shows an empty state with guidance (e.g. "No boards found—check permissions or try another account") rather than failing silently.

## Dev Tasks

1. **Framework design doc (research phase)** – Integrations architect produces design doc that includes: (a) **Adapter interface** – method signatures (get_config, upsert_config, get_schema, test_connection, prepare_sync, auth hooks) and mapping to existing routes; (b) **Adapter vs connector** – separation between integration adapter (API/UI) and connector (sync), how config flows from adapter to connector, and that connectors must set source_id and source_system on entities; (c) **Auth** – per-provider auth type (OAuth2 vs API key) and required scopes for OAuth (e.g. Jira, Monday); (d) **Route strategy** – keep existing paths vs generic /integrations/{source_id}, delegation from route to adapter; (e) **Shared config/mapping model** – IntegrationConfig and EntityMappingConfig (source discriminator, optional source-specific fields); (f) **UI contract** – wizard steps, pluggable auth and schema loaders, shared field-mapping component (searchable dropdown), how connection status is exposed; (g) **Sync model** – default to pull/sync; webhooks/push out of scope for framework unless specified per integration. Covers: F1, F2, F3. Estimated: Medium.

2. **Implement adapter interface and registry** – Define integration adapter interface (get_config, upsert_config, get_schema, test_connection, prepare_sync, auth hooks); implement registry by source_id; abstract auth (OAuth vs API key). Covers: F1, F3. Estimated: High.

3. **Unified config and mapping model** – Introduce generic IntegrationConfig and EntityMappingConfig (source discriminator); refactor API to use them; ensure backward compatibility for stored Monday/Jira config. Covers: F2. Estimated: Medium.

4. **Migrate Monday to adapter** – Implement adapter for Monday; delegate existing /integrations/monday routes to adapter; preserve behavior. Covers: F8. Estimated: High.

5. **Migrate Jira to adapter** – Implement adapter for Jira; delegate existing /integrations/jira routes to adapter; preserve OAuth and behavior. Covers: F8. Estimated: High.

6. **Single wizard flow and shared field-mapping UX** – One wizard (Select entities → Auth → Select source types → Field mapping → Test & Sync) used in onboarding and integration settings; shared searchable-dropdown component for field mapping; pluggable auth and schema loaders per integration. Covers: F4, F5. Estimated: High.

7. **Contract tests** – Contract tests for adapter interface; at least one contract test per adapter (Monday, Jira) with mocked external APIs. Covers: F7. Estimated: Medium.

8. **New-integration checklist doc** – Document steps to add a new integration: implement adapter, register, add to UI; reference adapter interface and UI contract. Covers: F6. Estimated: Low.

## Test Strategy

- Unit tests for adapter interface and shared config/mapping models.
- Contract tests per adapter (mocked external APIs) for config, schema, test, prepare.
- Integration tests: run wizard flow for Monday and Jira against test/staging credentials or mocks; verify config round-trip and sync trigger.
- No new flaky E2E browser tests required; prefer high-fidelity unit and contract tests per product-os-integrations-architect.
