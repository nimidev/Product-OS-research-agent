# US-008: Research Agent – Pro Product Researcher Chat Experience

## Metadata
- **Repo**: `Product-OS-Research-Agent`
- **ID**: US-008
- **Status**: `dev`
- **Branch**: `feature/US-008-pro-researcher-chat`
- **Dependencies**: US-001 (core Research Agent), US-002 (canonical entity model), US-003 (Product OS UI integration)

## Goal

Transform the Research Agent chat into a professional-grade product researcher for product managers that (1) provides a consolidated glass pane over all relevant product entities, and (2) runs deep cross-entity research to surface non-obvious insights, combining clear bottom-line conclusions with the ability to deep dive into detailed analysis and complex follow-up questions.

## Success Metrics

Targets to be set at kickoff (or after first reference-answer eval). Example initial targets:

- **SM1 – PM satisfaction with answers**: ≥ 70% of PM sessions rated as “high quality / very helpful” in an in-product feedback prompt.
- **SM2 – Reduction in manual research time**: Median time to answer a standard product research question reduced vs baseline (target TBD via task-based study or logs).
- **SM3 – Grounding quality**: In evaluation, ≥ 85% of sampled answers rated as “properly grounded in entity data” with no major hallucinations.
- **SM4 – Depth of insight**: In evaluation, ≥ 80% of sampled deep-research answers contain at least 2 cross-entity insights (not just single-source restatements).

## Problem Statement

The current Research Agent chat experience feels dull and generic, does not consistently behave like an expert product researcher, and does not fully leverage entity data or product research best practices. Product managers must manually hunt for relevant entities across multiple tools, stitch context together into a single document, and then use external LLMs (ChatGPT/Claude/Gemini) for analysis. This is slow, error-prone, and makes it hard to connect data points across entities to get high-quality, insight-driven answers. Users expect a ChatGPT/Claude-quality conversational experience that is fine-tuned to the organization’s product entities and workflows, acting as a consolidated glasspane and deep research assistant rather than a thin chat wrapper.

## Target Users

- Primary: Product Managers responsible for defining, shipping, and iterating on Product OS features.
- Secondary: Product leadership and adjacent roles (e.g. founders, product analysts) who need fast, deep product insights grounded in organizational data.

## Non-Goals

- This story does not cover building new data connectors or expanding the underlying entity schema beyond what is required to support richer research behavior.
- This story does not aim to replace generic LLM usage across the organization; it focuses specifically on the Research Agent chat experience.
- This story does not define a full visual redesign of the UI; UI changes are limited to what is needed to support better research flows, structure, and affordances.
- The agent does not act as a generic PM education bot; it should avoid long theoretical explanations unless explicitly requested.
- The agent does not edit or maintain product documentation; it can summarize or reference docs but not own them.
- The agent does not execute changes in external tools (roadmaps, tickets, experiments); it only recommends actions.
- The agent does not fabricate metrics or entity data; any assumptions or estimates must be explicitly labeled as such.
- The agent does not optimize for “feel-good” answers; it should surface real problems and risks even when they are uncomfortable.

## Acceptance Criteria

AC1 – Dynamic response structure  
- For simple, fact-based questions (e.g. counts, basic filters), the agent returns a short, direct answer (1–3 sentences) plus minimal context, without forcing a heavy multi-section layout.  
- For complex or research-oriented questions (e.g. “how is X performing and what should we do next?”), the agent uses a structured response pattern with some or all of:
  - TL;DR / Bottom Line
  - Key Insights
  - Evidence / Data Sources
  - Recommendations / Next Actions
  - Optional Deep Dives (e.g. user feedback, usage patterns, revenue impact), chosen based on question type and available data.

AC2 – Intent & scope resolution  
- For each question, the agent infers:
  - Question type (lookup vs diagnostic vs strategy/recommendation vs exploratory).  
  - Target product(s)/feature(s)/segments.  
  - Relevant timeframe (explicit in the question or inferred from defaults, and clearly stated in the answer).  
- The inferred scope is either explicitly stated in the answer or clearly implied in a way that a PM can verify (e.g. “Looking at the last 90 days for Product X…”).

AC3 – Systematic research playbook  
Given a non-trivial research question, the agent follows a consistent playbook before answering (conceptually, not necessarily step-by-step exposed in UI):
- Interprets the intent and depth required (quick lookup vs deep research).  
- Resolves which products/features/entities and timeframes are in scope.  
- Identifies relevant entity types to query (e.g. usage/telemetry, revenue/impact, support tickets, product feedback, experiments, roadmap items, goals/OKRs).  
- Pulls data from each relevant entity type with appropriate filters (timeframe, segments, severity, etc.).  
- Assesses data coverage and calls out meaningful gaps (e.g. “no recent feedback”, “few tickets – low volume”).  
- Runs cross-entity analysis to find patterns (e.g. themes across support + feedback, correlations between usage drops and ticket spikes, gaps vs roadmap).  
- Synthesizes candidate insights and prioritizes them by impact and confidence.  
- Only then formats the response, choosing the appropriate structure per AC1.

AC4 – Cross-entity insight generation  
- For research-style questions, the agent uses **multiple** entity types when available (not just a single source) and explicitly connects signals across them (e.g. “high usage but rising support tickets about performance”).  
- The answer clearly distinguishes:
  - Facts directly grounded in entity data.  
  - Interpretations/insights built on those facts.  
  - Explicit assumptions or hypotheses when data is missing or weak.

AC5 – Honesty, directness, and emphasis on problems  
- The tone is straightforward and concise; the agent avoids filler, “salesy” language, or over-apologizing.  
- When the data indicates real problems or risks (e.g. poor adoption, strong negative feedback, major gaps), the answer highlights them prominently in the TL;DR and Key Insights sections.  
- The agent is allowed (and expected) to say “we don’t know” or “data is insufficient” with suggestions for what data would be needed to answer properly.  
- When no relevant entities are found for the question, the agent states that clearly (e.g. “No relevant [entity type] found for this scope”) and does not infer from generic knowledge alone.

AC6 – Transparency of evidence  
- For non-trivial answers, the agent references which entity types and timeframes were used (e.g. “support tickets (last 90 days)”, “NPS verbatims (last 30 days)”, “usage events for feature X (last 14 days)”).  
- Where supported by the UI, the agent links to or names concrete entities/samples (e.g. top 3 representative tickets or feedback items) rather than only speaking in aggregates.

AC7 – Grounding over generic LLM behavior  
- Answers are grounded in the organization’s entities and product context by default; generic product advice is only added as a thin layer on top of grounded insights, not as a substitute.  
- If the question is purely generic and cannot be grounded (e.g. “what is a good product strategy framework?”), the agent either answers explicitly as generic guidance or asks a brief clarification to tie it back to the organization’s context.

## NFRs / Constraints

- **NFR1 – Latency vs depth**
  - For simple lookup questions: p95 response time ≤ 3s.
  - For deep research questions: p95 response time ≤ 8s, with visible “researching” state if > 4s.

- **NFR2 – Grounding & hallucinations**
  - The agent must not invent entity records or metrics; when data is missing or incomplete, it must say so explicitly.
  - Critical quantitative claims (metrics, counts, trends) must be grounded in retrievable entities.

- **NFR3 – Deterministic structure**
  - For deep research questions, ≥ 90% of answers follow the structured pattern (TL;DR, Key Insights, Evidence, Recommendations, optional Deep Dives).
  - For simple lookup questions, ≥ 90% of answers avoid unnecessary sections and stay concise.

- **NFR4 – Safety & data scope**
  - The agent only uses entities and data sources explicitly configured for the Research Agent; no external internet access unless explicitly enabled.
  - Sensitive fields (if any) must respect existing access controls (out of scope to change here, but behavior must not bypass them).

- **NFR5 – Evaluationability**
  - Behavior defined in ACs must be testable via offline evals or scripted prompts (e.g. a questions suite in `questions.md`).

- **NFR6 – Failure handling**
  - On LLM or retrieval failure (timeout, API error, empty pipeline), the agent returns a short, honest error message (e.g. “Research unavailable right now; try again in a moment”) and does not show a partial or hallucinated answer.

## Reference answers (gold set)

- The canonical question set is **[questions.md](./questions.md)**.
- **Reference (gold) answers** for a representative subset are in **[reference_answers.md](./reference_answers.md)**. They define how optimal Q&A should look: structure (simple vs deep), tone, grounding, and cross-entity usage per AC1–AC7.
- Store reference answers in a dedicated artifact (e.g. `reference_answers.md` in this folder, or a structured format under `data/fixtures/`) so they can be used for:
  - **Model selection**: compare candidate models against the gold set (quality, structure, latency).
  - **Regression evals**: ensure new prompts/models do not regress on these exemplars.
  - **Onboarding**: clear expectations for PMs and engineers on what “good” looks like.
- Cover at least: 1–2 simple lookups, 1–2 diagnostics, 1–2 strategy/synthesis questions, and 1–2 short single-artifact queries (see questions.md usage notes).

## Dev Tasks

1. **Define reference (gold) answers for the questions.md suite**
   - Select a representative subset of questions from `questions.md` (simple lookup, diagnostic, strategy/recommendation, exploratory, and short single-artifact).
   - Write optimal answers that satisfy AC1–AC7: correct structure (short vs full TL;DR/Insights/Evidence/Recommendations), explicit scope/timeframe, cross-entity signals where relevant, honest “we don’t know” when appropriate, and clear evidence references.
   - Store in the agreed artifact (e.g. `reference_answers.md` or structured fixture); link from this PRD. Use this gold set as the benchmark for model selection and regression evals.

2. **Evaluate and select LLM model for research chat**
   - Compare current default (e.g. `gpt-4o-mini` in `.env`) against newer/more capable options (e.g. GPT-4o, Claude Opus/Sonnet, or other providers) on: answer quality (grounding, depth, structure), latency (vs NFR1), and cost.
   - Run evaluation against the `questions.md` suite and **reference answers**; document results and recommend a default model for the pro-researcher experience.
   - Update `.env` (and any config docs) with the chosen model; support switching models via config for future A/B or fallback.

3. **Design chat behavior & prompt schema for research playbook**
   - Encode AC1–AC7 into system/instruction prompts and routing logic.

4. **Implement entity-scoped research pipeline**
   - Given a question, resolve scope, select entity types, fetch data, and expose a structured context to the LLM.

5. **Implement structured response renderer**
   - Support dynamic selection between simple and deep-response layouts, including TL;DR, insights, evidence, recommendations, and deep-dive sections.

6. **Integrate questions evaluation suite**
   - Wire `questions.md` and the **reference answers** into an eval harness; score agent output on structure, grounding, depth, and cross-entity usage against the gold set.

7. **Telemetry & feedback collection**
   - Capture per-answer metadata (question type, entities used, sections included) and PM feedback to track success metrics.

8. **Guardrails for grounding & honesty**
   - Add checks/logging for hallucination-prone behaviors and explicit messaging when data is missing.

## Test Strategy

### TS1 – Prompt evaluation suite and reference answers

- Maintain a curated set of representative questions in **questions.md** covering:
  - Simple lookups (counts, filters)
  - Diagnostics (“what’s going wrong?”)
  - Strategy/recommendation (“what should we do?”)
  - Exploratory/what-if questions
  - Short single-artifact queries (see questions.md usage notes)
- Maintain **reference (gold) answers** for a subset of these questions (see [Reference answers (gold set)](#reference-answers-gold-set)); for each reference answer, document:
  - Expected structure (simple vs deep)
  - Key entities involved
  - Qualitative acceptance notes
- Use reference answers as the benchmark for “how good should this look?” in model selection and regression runs.

### TS2 – Offline eval

- Run periodic offline evals of the question suite against the **reference answers**:
  - Score agent output on: grounding, depth of insight, structure, honesty/no-fluff, and cross-entity usage (and optionally similarity to gold structure/content where applicable).
  - Track a composite score and regressions over time.

### TS3 – Manual PM review

- For first release, run at least N real PM sessions (N to be set at kickoff; e.g. 10–20) where:
  - PMs perform real tasks using the agent.
  - They rate each answer on usefulness, trust, and depth.
  - Findings are fed back into prompt/behavior tuning.

### TS4 – Regression checks

- Before major model/prompt changes, rerun the suite and compare against previous baseline; do not ship if score drops more than X% on grounding or depth (X to be set at kickoff).
- Include a check that on simulated LLM/retrieval failure, the agent returns the NFR6 error message and does not surface partial or hallucinated content.

## Examples – Bad vs Good Answers (Illustrative)

- **Bad (generic/dull)**  
  - “Feature X seems to be doing okay. Some users like it and some don’t. You could consider improving performance and usability.”

- **Good (pro product researcher)**  
  - “TL;DR: Feature X adoption is strong in self-serve teams but lagging in enterprise accounts; performance-related complaints have spiked in the last 30 days, especially for large boards.  
    - **Key Insights:**  
      - Usage for Feature X grew +28% MoM overall, but only +5% in enterprise workspaces.  
      - Support tickets mentioning “slow” or “performance” related to Feature X increased from 3 → 19 in the last 30 days, mostly from accounts with >50 active users.  
      - There is no active roadmap item addressing performance for large boards, despite repeated feedback from top-ARR customers.  
    - **Recommendations:** Prioritize a performance-focused iteration for enterprise-scale workspaces and instrument separate metrics for large vs small boards.”
