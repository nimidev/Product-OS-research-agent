# US-003: Product OS UI and Integration Service (Phase 1 – Monday.com)

## Metadata

- **Repo**: `Product-OS-Research-Agent`
- **ID**: US-003
- **Status**: `done`
- **Branch**: `feature/US-003-ui-integration-monday-mvp`
- **Dependencies**: US-001 (Research Agent core), US-002 (canonical entity model – entities ingested must align with canonical schema and search_memories/list_sources)

## Goal

Apply the Product OS UI prototype (from [Product-OS-UI](https://github.com/nimidev/Product-OS-UI.git)) into the Research Agent repo so the research agent works with that UI, and deliver an integration service that is the backend for the UI’s integration settings—enabling simple, efficient ingestion and sync with entity data sources. Phase 1 scope: Monday.com only; all other sources (Jira, Notion, Google Docs, etc.) are shown in the UI as “coming soon.” Chat must work and return answers based on ingested Monday data; integration configuration must result in entities being ingested and searchable via `search_memories` and `list_sources`.

## Problem Statement

The Research Agent today is used via MCP (Cursor) and REST API only. There is a separate UI prototype (Product-OS-UI) that demonstrates integrations with multiple data sources and a chat interface. To make the research agent usable through that UI, we need to: (1) integrate the UI into the Research Agent repo and wire it to the existing API; (2) provide a backend for integration settings so that configuring a source (starting with Monday.com) results in real ingestion and sync into the Research Agent’s canonical store and vector index, and chat answers are grounded in that data.

## Target Users

Product managers and teams who will use the Research Agent via the new UI; operators who configure data sources (Monday.com in Phase 1) through the integration settings in the UI.

## Non-Goals (Phase 1)

- Additional data source integrations (Jira, Notion, Google Docs, etc.)—handled in separate future PRDs per integration; UI shows them as “coming soon.”
- Product Context Sidebar, chat response entity labels, and suggested next question—these exist in the prototype; tracked as US-004, US-005, US-006 for future phases; not delivered in Phase 1 MVP.

## Success Criteria

1. **Successful integration with Monday.com** — User can configure Monday.com in the UI; credentials/settings are stored and used by the integration service to sync boards/items into the Research Agent.
2. **Chat works with ingested data** — Chat in the UI sends queries to the Research Agent; answers are based on ingested data from the Monday integration (synthesis + citations from search_memories).
3. **Configuration of integrations is successful** — Relevant entities from Monday are ingested into the Research Agent database (canonical entities + chunks + Qdrant); they are searchable via `search_memories` and visible via `list_sources`. Other integrations in the UI are labelled “coming soon.”

## Out of Scope for Phase 1 (Future PRDs)

- **US-004**: Product Context Sidebar (from prototype).
- **US-005**: Chat response entity labels (from prototype).
- **US-006**: Suggested next question (from prototype).
- Additional integrations: one PRD per new source (Jira, Notion, Google Docs, etc.) when needed.

## Acceptance Criteria

- **AC1** – The Product-OS-UI codebase (or its relevant frontend) is integrated into the Research Agent repo (or served from it) so that the Research Agent is the backend for that UI.
- **AC2** – The UI displays an integration settings area where Monday.com can be configured (e.g. API token, board/workspace selection as needed); all other listed sources (Jira, Notion, Google Docs, etc.) are visibly labelled “coming soon” and not configurable in Phase 1.
- **AC3** – An integration service (backend) persists integration configuration (e.g. Monday API token, board IDs) and exposes endpoints used by the UI for “save/test” of integrations; Phase 1 implements this for Monday.com only.
- **AC4** – When Monday.com is configured and sync runs, Monday data is ingested into the Research Agent’s canonical store (entities + entity_fields + chunks per US-002) and embedded into Qdrant; sync is triggerable from the integration service or existing sync flow.
- **AC5** – Entities ingested from Monday appear in `list_sources` and are searchable via `search_memories`; chat in the UI uses these endpoints (or equivalent) and returns answers with citations from the ingested Monday data.
- **AC6** – End-to-end: configure Monday in UI → run sync → ask a chat question that depends on Monday data → response is grounded in that data with correct citations.
- **AC7** – Sync interval from Monday to Product OS is configurable (e.g. in integration settings or backend config); default is every 2 hours.
- **AC8** – The UI provides flexible mapping configuration so that only relevant Product OS entity types are populated from Monday: user can configure which Monday board(s) and/or item types map to which canonical entity types (e.g. feature_request, bug, roadmap_item). Unmapped or excluded boards/items are not ingested, so junk data is avoided and only intended entities are searchable.
- **AC9** – Before implementing the chat UI, search is verified via MCP and/or REST API (`search_memories`, `list_sources`) using ingested Monday data; this checkpoint test passes before chat interface development continues.

## NFRs / Constraints

- UI and integration service must work with the existing Research Agent API and canonical model (US-002); no schema changes required for Phase 1.
- Integration credentials (e.g. Monday API token) must be stored securely (e.g. env or secure config); no secrets in frontend or logs.
- Sync must be efficient (incremental where possible, consistent with existing connector behavior). Sync schedule is configurable; default interval 2 hours.

## Edge Cases & Error Handling

- **Invalid or expired Monday credentials:** Integration service or sync must not crash; return clear error in UI (e.g. "Connection failed – check API token") and log; do not ingest partial data.
- **Sync failure (network, rate limit):** Per-connector isolation; failed sync is logged and retried on next scheduled run; other data unchanged.
- **No boards / empty mapping:** If user has not mapped any board to an entity type, sync runs but ingests nothing for Monday; list_sources still reflects other sources if any.
