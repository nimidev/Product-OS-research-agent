# US-011: Seamless Onboarding & Setup Experience for New Users

## Metadata
- **Repo**: `Product-OS-Research-Agent`
- **ID**: US-011
- **Status**: `dev`
- **Branch**: `feature/US-011-seamless-onboarding`
- **Dependencies**: None (builds on existing integration system from US-003/US-007/US-009)

## Target Users
- **Primary**: Product Managers evaluating the Research Agent — non-technical, cloning from GitHub, running locally to prove value with their own organizational data.
- **Secondary**: IT / admin users who may later deploy to production after the PM validates the product.

## Goal

Deliver a frictionless, high-completion-rate onboarding experience that takes a PM from `git clone` to asking their first real research question against their own organizational data — in under 15 minutes, with a single CLI command and a guided UI flow, no Docker required.

## Problem Statement

Today's setup requires 8+ manual steps across 3 ecosystems (Python, Docker, Node.js), including installing Docker Desktop (~1GB, admin privileges, enterprise licensing friction), manually editing config files, and running multiple services with no validation or guidance. There is no first-run detection in the UI — users land on an empty chat with no direction. The result is a high drop-off rate for non-technical evaluators who are the primary target users.

**Key friction points identified through research:**
1. Docker is required for Qdrant — most PMs don't have it and won't install it
2. No guided flow — README wall-of-text with 8+ manual steps
3. No validation — failures are silent or cryptic
4. No first-run experience — UI shows empty state with no onboarding
5. Integration setup (connecting real data) is separate from app setup, requiring a second discovery

## Success Metric

85%+ of users who start `python -m research_agent setup` complete the full onboarding (CLI + UI) and run their first real query. Measured via manual test sessions during development; telemetry instrumentation is a future consideration (not in scope).

## Non-Goals

- MCP / Cursor configuration (future task)
- Adding new integration types (JIRA, Notion, Linear — separate PRD per US-007 scope)
- Docker mode setup automation (documented upgrade path only)
- CSV/JSON upload for entity types not tracked in a supported tool
- Mock/sample data seeding (real data from integrations only)
- Mobile-first design (desktop/web primary)
- Replacing the existing Integration Settings page (onboarding extends it with a first-run flow)

## Acceptance Criteria

### AC1: Single-command CLI setup wizard
**Given** a user has cloned the repo and has Python 3.11+ installed
**When** they run `python -m research_agent setup`
**Then** an interactive CLI wizard guides them through:
1. Environment check (Python version, Node.js presence, Docker presence)
2. Dependency installation (auto-create venv + `pip install`, `npm install` if Node.js found)
3. OpenAI API key input (interactive prompt with link to platform.openai.com, immediate validation via test embedding call)
4. Qdrant local mode initialization (automatic, no user action)
5. Database creation (automatic)
6. Service startup (API on :8000, UI on :3000 if Node.js available)
7. Auto-open browser to UI

### AC2: Qdrant local mode as default storage backend
**Given** the setup wizard runs
**When** it checks for Docker
**Then** it defaults to Qdrant local mode (file-based, `AsyncQdrantClient(path="./qdrant_data")`) regardless of Docker availability. The `QdrantStore` class accepts either `host`+`port` (server mode) or `path` (local mode) parameters. All existing callers continue to work via a config-driven selection (`QDRANT_MODE=local|server` env var, default `local`).

### AC3: UI first-run onboarding flow
**Given** a user opens the UI for the first time (no integrations configured)
**When** the UI loads
**Then** instead of the empty chat, a guided onboarding flow is shown:
- **Step 1 — Entity mapping**: "Where does your team track these?" — for each Product OS entity type (Feature Requests, Bugs, Support Tickets, Roadmap Items, PRDs, Meeting Notes), user selects a tool from supported integrations or "Not tracked yet" (skip)
- **Step 2 — Connect tool**: For each unique tool selected, prompt for API key + validate (reuse existing test endpoints)
- **Step 3 — Board/project mapping**: For each entity type → tool pair, select the board/project/database and map fields (reuse existing mapping UI with smart defaults pre-filled)
- **Step 4 — Sync & Index**: Trigger sync for all configured entities with a progress indicator showing per-entity-type progress and total items/vectors indexed
- **Step 5 — First query**: "You're all set!" with a pre-filled suggestion question relevant to the entity types they connected, plus a text input to ask their own

### AC4: Onboarding writes to existing integration system
**Given** the user completes the UI onboarding flow
**When** they navigate to the Integration Settings page
**Then** their configuration (API keys, board mappings, entity mappings, field mappings) is fully visible and editable — the onboarding wrote to the same `IntegrationConfigRow` and mapping data as the existing settings page. No duplication.

### AC5: Vector count monitoring with limit enforcement
**Given** the app is running in Qdrant local mode
**When** vector count reaches 80% of the 20,000 threshold (≥16,000 vectors)
**Then** a warning notification/widget appears in the UI: "You're using 16,000 / 20,000 vectors. Consider upgrading to Docker or Cloud mode for better performance."
**When** vector count reaches 20,000
**Then** further ingestion is blocked with a clear message: "Vector limit reached. To continue adding data, upgrade to Docker mode or Qdrant Cloud." with a link to upgrade instructions. Existing data remains fully searchable.

**Upgrade path (documented):** The upgrade instructions page/section covers:
1. Install Docker and start Docker Desktop
2. Run `docker-compose up qdrant -d`
3. Set `QDRANT_MODE=server` in `.env`
4. Run `python -m research_agent reindex` to migrate vectors from local storage to the Qdrant server
5. Restart the API (`python -m research_agent serve`)

### AC6: Health check / doctor command
**Given** the user has run setup (or wants to diagnose issues)
**When** they run `python -m research_agent doctor`
**Then** it checks and reports status for:
- Python version (✓/✗)
- Dependencies installed (✓/✗)
- OpenAI API key configured and valid (✓/✗)
- Qdrant storage accessible and mode (local/server) (✓/✗)
- Database exists and schema is current (✓/✗)
- Vector count and limit status (X / 20,000)
- API server reachable (✓/✗, if running)
- UI server reachable (✓/✗, if running)

### AC7: Idempotent setup
**Given** the user has already completed setup (partially or fully)
**When** they run `python -m research_agent setup` again
**Then** the wizard detects completed steps (venv exists, deps installed, .env has API key, DB exists, etc.), skips them, and only runs remaining/broken steps. It never overwrites existing configuration without confirmation.

### AC8: Graceful Node.js fallback
**Given** the user does not have Node.js installed
**When** the CLI wizard runs
**Then** it completes all Python-based setup (API, storage, deps), clearly states "Node.js 20+ is needed for the web interface", provides install instructions (link to nodejs.org), and tells the user to re-run `python -m research_agent setup` or `python -m research_agent setup --ui` after installing Node.js. The API is fully functional for MCP/API consumers.

### AC9: Resumable UI onboarding
**Given** the user completes CLI setup but closes the browser before finishing UI onboarding
**When** they open the UI again
**Then** the onboarding flow is shown again (detected via "no integrations configured" state). Any partial progress within the UI onboarding (e.g., API key already saved) is preserved and pre-filled.

### AC10: Setup progress and time framing
**Given** the CLI wizard starts
**When** each step begins and completes
**Then** a step indicator shows progress (e.g., "[3/5] OpenAI API Key") and the wizard displays an estimated total time ("This will take about 5 minutes") at the start.

## NFRs / Constraints

### Performance
- CLI wizard completes in < 5 minutes on a standard machine (excluding dependency download time)
- UI onboarding flow renders and transitions between steps in < 500ms
- First sync + index of ≤500 items completes in < 3 minutes
- Vector search latency in local mode < 200ms for ≤10,000 vectors (OpenAI API call dominates total latency regardless)

### Reliability
- Setup wizard never crashes on bad input — validates, reports, and offers retry or skip
- If OpenAI key validation fails, offer retry with clear error ("Invalid key", "Billing not active", "Network error")
- If Qdrant local mode init fails (disk permissions, etc.), report and suggest fix
- All setup state is persisted to `.env` and DB — no in-memory-only config

### Compatibility
- macOS (primary), Linux, Windows (WSL)
- Python 3.11+
- Node.js 20+ (optional, for UI)
- No Docker required for default setup

### Security
- API keys stored in `.env` (gitignored) and `IntegrationConfigRow` (local DB), never logged or displayed after input
- OpenAI key masked in CLI output after first 4 characters

### UX Standards
- CLI uses colored output (green ✓, red ✗, yellow ⚠) for status indicators
- UI onboarding follows existing design system (Tailwind, Lucide icons, motion animations)
- All error messages include actionable next steps, not just error codes

## Test Strategy

### Unit Tests
- `QdrantStore` with `path` parameter — init, upsert, search, count, close
- Config loader detects `QDRANT_MODE=local` and passes `path` instead of `host`+`port`
- Setup wizard step detection (idempotency logic)
- Vector limit enforcement (block at 20K, warn at 16K)

### Integration Tests
- Full CLI wizard run in a clean environment (temp dir, no existing config)
- Idempotent re-run after complete setup
- UI onboarding flow end-to-end (Playwright/Cypress)
- First-run detection → onboarding → settings page continuity

### Manual Test Scenarios
- PM persona: clone → setup → onboarding → first query (< 15 min)
- No Node.js: setup completes, clear instructions shown
- Bad API key: validation catches, offers retry
- Re-run setup: skips completed steps
- Close browser mid-onboarding: re-shows on next visit
- Approach 20K vector limit: warning shown, ingestion blocked at limit
