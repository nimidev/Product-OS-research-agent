# US-012: Backlog Integration – Jira (Atlassian)

## Metadata
- **Repo**: `Product-OS-Research-Agent`
- **ID**: US-012
- **Status**: `dev`
- **Branch**: `feature/US-012-jira-integration`
- **Dependencies**: US-003 (integration service), US-007 (entity/field mapping pattern). Delivers one dedicated Jira integration; mapping UX follows US-007 and mirrors the existing Monday.com flow with adaptations for Jira entities and fields.

## Target Users
- **Primary**: Admins configuring Jira as a data source for Product OS.
- **Secondary**: PMs and dev leads consuming Jira issues (roadmap, tasks, bugs, feature requests) in Research Agent search and chat.

## Goal

Deliver a **dedicated Jira integration** that provides a **simple integration and entity mapping experience** aligned with the existing Monday.com onboarding flow: connect Jira, choose which Product OS entities to sync, link each entity to the right Jira project/board scope, map **each Jira field** to canonical Product OS fields, test, and activate. Success = admins can complete connect → map → sync for Jira with the same level of clarity and ease as today’s Monday.com integration, adapted to Jira entities and Jira’s field model.

## Problem Statement

Product and dev teams use Jira for epics, stories, bugs, and tasks (and Jira Software boards/backlog/sprints). Without a dedicated integration, this data is invisible to the Research Agent. The integration must reuse the **same onboarding and integration flow** as Monday.com (Connect → Map → Sync): OAuth connect, scope selection (project/board), entity mapping (which Product OS entities to sync and which Jira issue types/projects they come from), and **field-level mapping** using real Jira fields (discovered via Jira API), so that the experience feels familiar and the deliverables are a simple, guided integration and entity mapping—not a one-off custom flow.

## Onboarding & integration flow (aligned with Monday.com)

The Jira integration **must maintain as similar as possible** the existing integration and entity mapping process, with adaptations for Jira:

1. **Connect** – Admin connects Jira via OAuth 2.0 in Product OS (same pattern as Monday connect). Credentials and selected cloud ID(s) stored; connection status visible.
2. **Choose entities** – Admin chooses which Product OS entity types to sync (roadmap_item, feature_request, bug, task, support_ticket), analogous to choosing Epics, Tasks, Bugs, Support in the Monday flow.
3. **Link to source** – For each chosen entity type, admin links to the right Jira scope: project(s) and/or board (and optionally backlog or sprint), analogous to linking to Monday boards.
4. **Map Jira issue types** – Admin maps Jira issue types (Epic, Story, Task, Bug, JSM request types) to the chosen Product OS entity types.
5. **Map fields** – For each entity type, the UI surfaces **real Jira fields** (from Jira Fields API) and the admin maps them to canonical Product OS fields (title, description, status, priority, etc.), including Jira Software custom fields (Epic link, Epic name, Sprint, Story points). Same idea as mapping Monday columns to Product OS fields.
6. **Test & activate** – Admin can run a test sync (sample from selected scope), review mapping result, then activate. Activation is only possible after a successful test sync (required per US-007 AC5). Only then does the integration participate in scheduled sync.

**Deliverables and success criteria** for this story are therefore: a **simple integration and entity mapping experience** for Jira, similar to the Monday.com one we have today, but based on Jira entities and each Jira field.

## Success Metrics

- **Mapping coverage**: Admins can map at least: roadmap_item (Epic), feature_request (Story or equivalent), bug (Bug), task (Task, Sub-task), support_ticket (JSM) from Jira.
- **Search grounding**: Queries about roadmap, bugs, feature requests, or tasks return Jira-backed entities in `search_memories` with citations to Jira issue URLs.
- **Setup completion**: A strong majority of admins who connect Jira can complete the full flow (connect → choose entities → link project/board → map issue types → map Jira fields → test sync → activate) for at least one project or board and one Product OS entity type without manual DB/CLI intervention—**comparable to Monday.com setup completion**.

## Technical Context (Research Summary)

- **Auth**: Atlassian OAuth 2.0 (3LO). Apps in [Atlassian Developer Console](https://developer.atlassian.com/cloud/oauth/). Token via `https://auth.atlassian.com/authorize` and `https://auth.atlassian.com/oauth/token`. API base: `https://api.atlassian.com`; use `accessible-resources` for cloud IDs and scopes.
- **Jira Platform**: REST API v3. Scopes (e.g. `read:jira-work`, `write:jira-work`, `read:jira-user`). Search: `GET /rest/api/3/search` with JQL, `maxResults` (default 50), `startAt`; max result window typically 10,000. Resources: issues, projects, issue types, fields (custom fields), comments. Use **Fields** API and issue **expand** to discover field IDs and values for mapping.
- **Jira Software (Agile)**: REST API `rest/agile/latest` (or `1.0`). **Board** (`/board`, `/board/{boardId}`), **Backlog** (`/board/{boardId}/backlog`), **Sprint** (`/board/{boardId}/sprint`, `/sprint/{sprintId}/issue`), **Epic** (board issues by epic). Jira Software custom fields (read via Platform issue resource): **Sprint** (schema `com.pyxis.greenhopper.jira:gh-sprint`), **Epic link**, **Epic name**, **Story points**; field IDs vary by instance (discover via Fields or createmeta).
- **Entity mapping**: See **Jira → Product OS mapping** below.

## Jira → Product OS mapping (reference)

Ensures integration supports dev-team tasks and roadmap items and maps successfully to Product OS entities using Jira entities and fields.

| Product OS entity   | Jira source(s) | Canonical fields to map (US-002) |
|---------------------|----------------|----------------------------------|
| **roadmap_item**    | Epic (Jira Software) | title, description, target_start, target_end, status, priority |
| **feature_request** | Story, "New Feature" (or custom issue type) | title, description, customer, priority, status, votes |
| **bug**             | Bug | title, description, severity, status, affected_version, priority |
| **task**            | Task, Sub-task | title, description, status, priority; parent epic/link if available |
| **support_ticket**  | Jira Service Management request type (optional) | title, description, customer, priority, status, resolution |

**Jira integration options to support:**

1. **Project + issue type**: Sync by project key(s) and issue type (e.g. project=PROJ AND issuetype=Epic). Issue types discovered via project metadata or createmeta/Fields.
2. **Board + backlog (Jira Software)**: Optional scope "board's backlog" — `GET /rest/agile/1.0/board/{boardId}/backlog`; issues include Epic, Story, Task, Bug per board config.
3. **Board + sprints**: Optional scope by sprint(s); `GET /rest/agile/1.0/sprint/{sprintId}/issue` for issues in sprint.
4. **Epic link / parent**: For roadmap_item and task, preserve Epic link (custom field) so tasks associate to roadmap items (epics). Field IDs discovered at runtime.

**Field mapping (Jira):** Use Jira Platform Fields API to list fields; map standard (summary → title, description → description, status → status, priority → priority) and Jira Software custom (Story points, Epic link, Epic name, Sprint) to canonical fields. For roadmap_item, map duedate or custom "target start/end" if present to target_start, target_end.

## Jira app configuration (OAuth 2.0 3LO)

Follow [Atlassian OAuth 2.0 (3LO) for Jira Cloud](https://developer.atlassian.com/cloud/jira/platform/oauth-2-3lo-apps/):

1. **Add APIs and scopes** (required first; otherwise you get “Your app doesn't have any APIs”):
   - In the console: **Permissions** → add **Jira platform REST API** (and optionally **Jira Software Cloud REST API**).
   - Add scopes: `read:jira-work`, `read:jira-user`, and `offline_access` (for refresh tokens).
2. **Callback URL:** **Authorization** → **Configure** (OAuth 2.0 3LO) → **Callback URLs**:
   - Local: `http://localhost:8000/integrations/jira/oauth/callback`
   - Production: `https://<your-api-host>/integrations/jira/oauth/callback`
3. **Settings (app auth):** Copy **Client ID** and **Secret** into the server env vars `JIRA_OAUTH_CLIENT_ID` and `JIRA_OAUTH_CLIENT_SECRET`. (Cloud ID is not in Settings — it is returned automatically when users complete “Connect with Jira (OAuth)”.)

Full step-by-step (APIs, scopes, env, troubleshooting) is in [docs/JIRA_OAUTH_SETUP.md](../../docs/JIRA_OAUTH_SETUP.md) in the Research Agent repo.

## Acceptance Criteria

- **AC1 – Connect**  
  Admin can connect Jira via OAuth 2.0 in Product OS integration settings, in the same way as connecting Monday. Credentials and selected cloud ID(s) are stored securely; connection status is visible in UI.

- **AC2 – Select scope**  
  Admin can choose which Jira projects and/or Jira Software boards to sync (and optionally restrict to backlog or specific sprint(s)). At least one project or one board must be selectable; selection is persisted and used as filter for sync. Flow mirrors Monday “link to board” step, adapted to Jira project/board.

- **AC3 – Entity mapping**  
  Admin can map Jira issue types (and optionally JSM request types) to Product OS entity types: **roadmap_item** (Epic), **feature_request** (Story or equivalent), **bug** (Bug), **task** (Task, Sub-task), **support_ticket** (JSM). Mapping follows US-007 pattern (entity → source project/board/scope, then field mapping). Experience analogous to choosing and linking Monday entity types to boards.

- **AC4 – Field mapping**  
  For each entity type, the UI surfaces **real Jira fields** for the selected project/board (fetched via Jira Fields API). Admin maps Jira fields (standard + Jira Software custom: Epic link, Epic name, Sprint, Story points) to canonical Product OS fields. Required canonical fields per entity type must be mappable; mapping cannot be saved until required fields are mapped. Mirrors Monday “map columns to Product OS fields” step.

- **AC5 – Test sync before activate**  
  Admin can trigger a test sync (sample from selected scope) before activating. Activation is only possible after a successful test sync returns at least one item (or explicitly confirms empty scope). Per US-007 AC5.

- **AC6 – Sync and ingestion**  
  Sync job (scheduled or on-demand) fetches issues from selected Jira project(s) and/or board backlog/sprint(s), normalizes to canonical entities + entity_fields + chunks (including Epic link for task → roadmap_item where present), and ingests into Research Agent store and vector index. Incremental sync (e.g. by `updated`) when APIs support it.

- **AC7 – Search and citations**  
  Ingested Jira issues appear in `list_sources` and `search_memories` with correct entity_type and citations to Jira issue URLs.

- **AC8 – NFRs**  
  Credentials stored server-side only; no secrets in frontend or logs. Rate limits and pagination respected (Jira 10k window). Clear errors for expired/invalid OAuth or missing scopes.

## Edge Cases & Error Handling

- **Invalid or expired OAuth token** → Clear error in UI with CTA to re-authenticate; sync does not run until token is valid.
- **No accessible projects/boards or issue types** → Explain in UI and block activation until at least one project or board and required issue types are available.
- **Selected project/board has no issues** → Sync completes successfully with 0 entities ingested; UI shows empty state or count 0; integration can still be activated.
- **User cancels or leaves before completing mapping** → Integration remains in "connected but not configured" state; it does not participate in sync until mapping is completed and activated (per US-007).
- **Jira result set exceeds 10k (max_result_window)** → Sync uses JQL date filters or splits by project/board so each request stays under limit; or document that only most recent 10k issues per scope are synced.
- **Missing required canonical field mapping** → Mapping cannot be saved; missing fields highlighted in UI (per US-007).
- **Jira API timeout or 5xx** → Log error, do not crash; retry on next scheduled run; other sources unchanged.

---

## NFRs / Constraints

- Use minimal OAuth scopes; read-only where one-way sync suffices.
- Sync must not crash on partial failures; log and retry on next run.
- Large Jira result sets: use JQL date filters or project split to stay within API limits.
- **UX parity**: Integration and entity mapping flow must remain as close as practicable to the existing Monday.com flow, with Jira-specific adaptations (projects/boards, Jira issue types, Jira fields).
