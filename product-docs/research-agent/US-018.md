# US-018: Memory & Retrieval Infrastructure Upgrade – Active Cross-Source Correlation

## Metadata
- **Repo**: `Product-OS-Research-Agent`
- **ID**: US-018
- **Status**: `in-progress`
- **Branch**: `feature/US-018-memory-retrieval-upgrade`
- **Dependencies**: US-001 (entity model), US-002 (canonical entity model), US-003 (Monday), US-012 (Jira), US-013–US-016 (future integrations), US-017 (integration framework)

## Target Users
- **Primary**: Product Managers using the Research Agent chat to surface insights across Jira, Monday, Productboard, Gong, SharePoint, and other sources.
- **Secondary**: Engineering team maintaining the retrieval pipeline (memory service, Qdrant store, embedding/chunking strategy).

## Goal

Upgrade the Research Agent's memory and retrieval infrastructure so that:
1. Cross-source correlation (e.g. a Jira bug ↔ a Gong call ↔ a Productboard feature describing the same theme) is actively discovered and stored as structured relationships.
2. Query understanding is driven by an LLM call rather than keyword heuristics, so intent is resolved accurately regardless of phrasing.
3. Retrieval quality improves with entity-level embeddings alongside chunk-level vectors, reducing noise from unrelated field fragments.
4. A lightweight nightly consolidation job synthesises new relationships and cross-cutting insights, inspired by the "always-on memory" pattern.

The outcome is a chat experience where asking "what are the top pain points for our onboarding flow?" reliably surfaces correlated evidence from every integrated source — not isolated fragments — without requiring ongoing manual tuning of keyword lists.

## Problem Statement

The current stack (Qdrant + SQLite + field-level chunking + heuristic query planner) has three compounding problems:

**1. Passive, island-based retrieval.** Each entity is stored and retrieved in isolation. There is no mechanism to surface that JIRA:BUG-42, a Gong call transcript, and a Productboard feature all reference the same customer pain point. The chat user must already know to ask the right scoped question; the agent cannot connect the dots proactively.

**2. Brittle query understanding.** `_classify_question()` and `infer_entity_scope()` are keyword lists (`memory_service.py:89`, `query_understanding.py:13`). They misclassify questions phrased differently from the expected keywords, over-restrict scope returning zero results, or miss intent entirely for compound/ambiguous questions. As more integrations are added, maintaining these lists becomes a maintenance burden with diminishing accuracy.

**3. Chunking loses entity context.** Field-level chunking (`add_or_update_entity`, `memory_service.py:453`) embeds individual fields (title, description, transcript) as independent vectors. A retrieval hit on a description chunk carries no information from the entity's title, status, or votes. Re-fetching the full entity from SQLite helps at synthesis time but does not improve ranking — irrelevant chunks score well and relevant entities rank poorly.

**Root cause:** The architecture is optimised for fast exact-field indexing but has no layer that actively processes, connects, and compresses information over time — the gap identified in comparing against the "always-on memory agent" pattern (Google ADK, 2026).

## Pre-Implementation Diagnostic & Current Baseline

Initial debug retrieval against a 22-question benchmark produced the following end-to-end search quality metrics:

- **Baseline (pre-US-018)** – Pass rate: **54.5%**, Avg P@5: **0.182**, Avg recall: **0.545**, **MRR: 0.245**.
- **After entity-level vectors + LLM planner + scoped search** – Pass rate: **59.1%**, Avg P@5: **0.245**, Avg recall: **0.591**, **MRR: 0.318**.

Failure modes have shifted from a mix of ranking issues and misses to primarily **true retrieval misses** on questions where the current corpus has little or no directly relevant data (e.g. GPT-4o launch decisions, competitor analysis).

This benchmark will be formalised in `tests/query_planner_benchmark.json` and `tests/test_query_planner_benchmark.py` in Phase 1 to satisfy AC6.

## Proposed Architecture

### Layer 1: Entity-level embeddings (fix retrieval quality)
Embed a synthesised entity summary — `{title} | {status} | {description[:500]}` — as a single dense vector per entity, stored alongside existing field-level chunk vectors. Use entity-level vectors as the primary ranking signal; chunk vectors for long-form fields (transcripts, PRD overview) only.

### Layer 2: LLM-based query planner (fix intent resolution)
Replace `_classify_question()` and `infer_entity_scope()` with a single `claude-haiku-4-5` call that returns structured JSON: `{question_type, depth, entity_types[], field_names[], source_filter}`. Cache the result in-request. Adds ~200ms latency; eliminates keyword maintenance and misclassification.

### Layer 3: Relation graph (fix cross-source correlation)
Add an `entity_relations` table to SQLite:

```sql
entity_relations (
  from_id      TEXT NOT NULL,   -- e.g. "jira:BUG-123"
  to_id        TEXT NOT NULL,   -- e.g. "productboard:feat-456"
  relation_type TEXT NOT NULL,  -- "same_theme" | "blocks" | "caused_by" | "mentioned_in"
  confidence   REAL NOT NULL,   -- 0.0–1.0
  created_at   TEXT NOT NULL,
  PRIMARY KEY (from_id, to_id, relation_type)
)
```

At query time, when top-K entities are retrieved, expand each result by one hop through this graph to surface correlated entities from other sources.

### Layer 4: Consolidation job (active cross-source linking)
A background job (runs post-sync, configurable interval, default: every 6 hours) uses `claude-haiku-4-5` to:
1. Cluster recently-added or updated entities by semantic proximity (batch embed → cluster by cosine distance threshold).
2. For each cluster, ask Claude to identify meaningful cross-source relations (same theme, causal, dependency).
3. Write confirmed relations (confidence ≥ 0.7) to `entity_relations`.
4. Optionally generate a short cross-cutting insight string stored on the cluster for use in synthesis.

This mirrors the consolidation pattern in the Google ADK "always-on memory agent" but scoped to structured product entities rather than free-form personal notes.

**Scale note:** At current scale (208 entities across 3 sources), the consolidation job will run trivially fast and produce few clusters. The 3-minute / 5,000-entity budget is a forward-looking constraint sized for the post-US-013–016 state when Gong transcripts, SharePoint documents, and additional boards are connected. The job should be built but not treated as a quality lever until data volume justifies it.

## Why Not Replace Qdrant?

Evaluated alternatives:

| Option | Assessment |
|---|---|
| **Google Always-On Memory Agent (ADK)** | No metadata filtering; reads all memories per query; breaks at multi-thousand entity scale; Gemini-only runtime. Not a fit. |
| **Weaviate / Vespa (hybrid BM25 + vector)** | Adds keyword recall for exact-match queries. High migration cost. Qdrant already supports sparse vectors (BM25-style) via the sparse index; can add this without migration. |
| **GraphRAG (Microsoft)** | Best-in-class cross-source correlation quality. Very high operational cost; requires full graph rebuild on each sync cycle. Consider in a future phase if relation graph proves insufficient. |
| **Mem0** | Wraps existing DB and adds cross-ref. Adds dependency and abstraction layer without solving the root embedding/planning problems. |

**Decision:** Keep Qdrant + SQLite; fix the three root problems (embeddings, query planner, cross-source linking) in the existing stack.

## Success Metrics

- **Baseline MRR established** via debug retrieval before any code changes (pre-implementation diagnostic).
- **Cross-source correlation**: ≥80% of manually validated entity pairs (same theme, different source) are linked in `entity_relations` after first consolidation run.
- **Query intent accuracy**: LLM planner correctly classifies question type and entity scope on a 20-question benchmark set (to be authored as part of this story), targeting ≥90% accuracy vs. ≤60% for current keyword heuristics.
- **Retrieval noise reduction**: Mean reciprocal rank (MRR) of entity-level embeddings ≥ chunk-level baseline established by the pre-implementation diagnostic.
- **Consolidation job runtime**: completes within 3 minutes for up to 5,000 entities; no blocking of API serving. At current scale (208 entities) this is not a meaningful constraint — metric is validated against projected post-integration scale.
- **No regression**: all existing `tests/test_api.py` and contract tests continue to pass.

## Non-Goals

- Replacing Qdrant with a different vector store.
- Full knowledge graph (GraphRAG) construction — relation graph is intentionally lightweight (flat edge table, not a property graph).
- Real-time consolidation on every sync event (batch/scheduled is sufficient).
- Exposing the relation graph in the UI in this story (chat synthesis uses it; no separate graph view).

## Scope Assumptions

- LLM calls in the query planner use `claude-haiku-4-5` (fast, low cost); `claude-sonnet-4-6` is not used in the hot path.
- Consolidation job is idempotent: re-running it on the same data produces no duplicates and does not degrade existing relations.
- Entity-level embedding uses the same `EmbeddingProvider` abstraction already in place; no new embedding model is required.
- `entity_relations` is populated by the consolidation job only; connectors do not write relations directly.

## Acceptance Criteria

- **AC1 – Entity-level embeddings and hybrid search** *(Phase 1)*
  Each entity upserted via `MemoryService.add_or_update_entity` generates one entity-summary vector (title + status + description[:500]) stored in Qdrant with `vector_type: "entity"` payload field, alongside existing field-level chunk vectors. Search path uses entity vectors as primary signal; chunk vectors as secondary for long-form fields. MRR on the pre-implementation diagnostic benchmark is equal or higher than baseline.

  Additionally, `QdrantStore.search` supports hybrid search combining dense (semantic) and sparse (BM25-style) vectors natively via Qdrant's sparse index — no migration required. Hybrid search is the default for all queries, ensuring exact-match queries on feature names, Jira ticket IDs, and metric names are not missed by pure semantic search.

- **AC2 – LLM-based query planner** *(Phase 1)*
  `_classify_question()` and `infer_entity_scope()` are replaced by an async `plan_research_llm(query, context)` function that calls `claude-haiku-4-5` and returns a `ResearchPlan`. A fallback (current heuristic) activates if the LLM call fails or times out (>2s). The planner achieves ≥90% accuracy on the 20-question benchmark set introduced in this story. The heuristic fallback caps `top_k` at 5; the current behaviour where a "why" question triggers all 6 entity types with `top_k=20+` is the primary noise source and must not be preserved in the fallback.

- **AC3 – Relation graph schema and DB layer** *(Phase 2; migration script may be written in Phase 1 as low-risk prep)*
  `entity_relations` table added to SQLite schema via migration. `Database` class exposes `upsert_relation`, `get_relations(entity_id)`, and `get_related_entities(entity_id, max_hops=1)` methods. Existing schema and data are unaffected.

- **AC4 – Graph expansion at query time** *(Phase 2)*
  `MemoryService.search_memories` expands top-K vector results by one hop through `entity_relations` and includes related entities (from other sources) in `raw_results` with a `relation_type` field. Related entities are ranked below direct vector hits unless their own vector score would place them higher.

- **AC5 – Consolidation job** *(Phase 2)*
  `research_agent/memory/consolidation.py` implements `ConsolidationJob` with a `run()` async method that: (a) clusters recently-updated entities by cosine similarity (threshold configurable, default 0.82), (b) calls `claude-haiku-4-5` to identify cross-source relations per cluster, (c) writes relations with `confidence ≥ 0.7` to `entity_relations`, (d) is callable from `__main__.py` as `--consolidate` flag and wired into the post-sync scheduler. Job is idempotent and completes within 3 minutes for 5,000 entities.

- **AC6 – Tests and benchmarks** *(partial in Phase 1; completed in Phase 2)*
  (a) Unit tests for `plan_research_llm` with mocked Claude API responses. *(Phase 1)*
  (b) A 20-question benchmark file `tests/query_planner_benchmark.json` covering lookup, diagnostic, strategy, and exploratory question types. Each entry must include: the question, expected `question_type` classification, expected `entity_types` list, expected `top_k` range (min/max acceptable), and a `ground_truth_entity_ids` list of Qdrant entity IDs that must appear in top results. A test asserts ≥90% classification accuracy AND measures MRR against ground truth retrievals. Ground truth is validated by a human PM before the test is committed. *(Phase 1)*
  (c) Unit tests for `ConsolidationJob` with mocked LLM and vector store. *(Phase 2)*
  (d) Unit tests for `get_related_entities` DB method. *(Phase 2)*
  (e) No regressions in `tests/test_api.py` or contract tests. *(both phases)*

## NFRs / Constraints

- **Latency**: LLM query planner adds ≤200ms p95 to search_memories; entity-level embedding adds ≤50ms to upsert (same batch embed call).
- **Cost**: Consolidation job uses `claude-haiku-4-5` only. Estimated cost: <$0.05 per consolidation run for 5,000 entities.
- **Backward compatibility**: Existing Qdrant points and SQLite entities remain valid; no re-index required except to backfill entity-level vectors (one-time migration script provided).
- **Observability**: Consolidation job logs: clusters found, relations written, relations skipped (low confidence), and wall-clock time.
- **Security**: No entity content is sent to external LLMs beyond what is already sent during synthesis (existing behaviour). Consolidation batches use the same summarizer/LLM client already configured.

---

## Edge Cases & Error Handling

- **LLM planner timeout/failure**: Fall back to heuristic planner (`_classify_question` + `infer_entity_scope`); log warning; do not fail the search request.
- **Consolidation cluster too large**: If a cluster contains >50 entities, split into sub-batches of 25 before sending to Claude to avoid context overflow.
- **Low-confidence relations**: Relations with `confidence < 0.7` are discarded and not written; logged at DEBUG level for observability.
- **Relation graph cycles**: `get_related_entities` is bounded to `max_hops=1` by default; graph traversal never recurses deeper without an explicit caller override.
- **Empty consolidation run**: If no entities were updated since the last run, the job exits early without calling the LLM.
