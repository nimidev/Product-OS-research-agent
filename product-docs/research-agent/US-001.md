# US-001: Research Agent – AI-Powered Organizational Knowledge Search

## Metadata

- **Repo**: `Product-OS-Research-Agent`
- **ID**: US-001
- **Status**: `dev`
- **Branch**: `feature/US-001-research-agent`
- **Dependencies**: None (standalone service; Product OS integration is a future add-on)

## Goal

Build a standalone Python service that syncs organizational data (Monday.com, Notion, and extensible to other sources) into a canonical store + vector database, and exposes semantic search via an MCP server for Cursor integration. Product managers can conduct multi-turn research conversations within Cursor, receiving AI-synthesized summaries with source references, to inform better product decisions and PRD creation.

## Problem Statement

Product managers make decisions based on scattered organizational knowledge: meeting notes in Notion, feature requests and roadmap items in Monday.com, bugs in issue trackers, past PRDs in various docs. Before writing a PRD, a PM must manually search across multiple tools, read through dozens of documents, and synthesize findings — a process that takes hours and often misses critical context.

There is no unified way to ask "what have customers said about X?" or "what decisions were made about Y?" across all organizational data. This leads to:
- Duplicate features being specced because past work is unknown
- Customer pain points being missed because feedback is buried in meeting notes
- Poor prioritization because the full picture isn't visible
- Slow ramp-up for new PMs joining a team

## Success Metrics

- **Adoption:** At least 1 PM uses `/research` weekly within 2 weeks of deployment
- **Query quality:** Search results contain relevant items in top-5 results for ≥ 80% of test queries (measured against a curated test set of 20+ queries with known-good answers)
- **Sync reliability:** Sync completes successfully ≥ 99% of scheduled runs with no silent data loss
- **Time to value:** A new user can go from `docker-compose up` to first useful query in < 15 minutes following the README
- **Synthesis accuracy:** AI-synthesized summaries correctly cite sources (no hallucinated references) in ≥ 95% of responses

## Non-Goals

- Replacing existing Product OS commands (`/create`, `/dev`, `/release`, `/verify`)
- Building a standalone web UI (Cursor chat is the primary interface)
- Real-time webhook-based sync (cron-style polling for v1; webhooks can be added later)
- Self-hosted / local embedding models in v1 (cloud API via OpenAI; provider is swappable)
- Full general-purpose AI chatbot (scoped to organizational knowledge retrieval)
- Write-back to source systems (read-only sync)
- Managing authentication/SSO for source systems (API keys/tokens in config)
- Product OS integration in this story (future story)
- Config hot-reload (changing `config.yaml` requires a service restart in v1)

## Acceptance Criteria

### Phase 1 — Demo Slice (Full Vertical with Mock Data)

> **Goal:** End-to-end working demo — a PM can `/research` in Cursor against a realistic mock dataset and get AI-synthesized answers with citations. Proves the core value proposition before building connector infrastructure.
>
> Phase 1 uses `.env` for secrets (OpenAI key) and Docker-internal defaults for Qdrant. The full `config.yaml` system arrives in Phase 2 (AC11).

- **AC1 – Canonical data model.** A single `Item` table exists in SQLite with fields: `id` (string, stable cross-system key, e.g. `mock:feature_request:042`), `source` (enum: mock/monday/notion/…), `type` (enum: roadmap_item/feature_request/support_ticket/bug/prd/meeting_note), `title`, `body` (full text), `metadata` (JSON: tags, customer, priority, url, etc.), `created_at` (datetime, from source system), `updated_at`, `content_hash`, `is_deleted`. CRUD operations work and are tested.

- **AC2 – Mock dataset (OpenAI ChatGPT).** A curated dataset of ~300-500 items representing the OpenAI ChatGPT product team is committed as JSON fixtures under `data/fixtures/`. Types include: feature requests (~100, sourced from real public discussions on Reddit, Twitter, OpenAI community forums), bugs/issues (~80, from known ChatGPT problems and community reports), roadmap items (~40, from public OpenAI announcements — GPT-4o, o1, Sora, memory, custom GPTs, Canvas, etc.), meeting notes (~80, fabricated but realistic PM sprint reviews, customer feedback sessions, prioritization discussions), PRDs (~30, fabricated based on real shipped features), and support tickets (~50, realistic patterns). Each item follows the canonical Item schema. Items contain overlapping themes (e.g., "enterprise data privacy" appears across feature requests, meeting notes, and roadmap items), temporal patterns (items span 12+ months), and cross-type relationships to enable meaningful search quality testing. A generator script (`scripts/generate_mock_data.py`) is provided alongside the committed output.

- **AC3 – Embedding pipeline & vector store.** Qdrant client wrapper supports: `upsert(id, vector, payload)`, `search(query_vector, filters, top_k) -> list[Result]`, and `delete(id)`. `EmbeddingProvider` interface with OpenAI `text-embedding-3-small` implementation (`embed` and `embed_batch`). Text chunking for documents exceeding 8,191 tokens (recursive splitter, ~500 token chunks, 50 token overlap, `parent_id` linkage). Search results de-duplicated by `parent_id`, ranked by best-chunk score. Provider swappable via config.

- **AC4 – Seed script & Docker infrastructure.** `docker-compose.yml` runs Qdrant and the Python service. A seed command (`python -m research_agent seed`) loads JSON fixtures into SQLite, embeds all items (with chunking for large docs), and upserts to Qdrant. A single `docker-compose up` followed by the seed command gets the full demo running. `Dockerfile` builds cleanly. Seed is idempotent (re-run safe via content_hash). Seed logs a warning if queried mid-run; partial data is searchable (not blocked) but may be incomplete until seed finishes.

- **AC5 – Memory service & REST API.** `memory_service` exposes `search_memories(query, filters, top_k)` and `add_or_update_item(item)`. FastAPI serves `POST /search_memories` accepting `{ query, filters, top_k }` and returning ranked results with item metadata and source URLs. Filters support: `source`, `type`, `date_range`, `tags`. Health check endpoint exists.

- **AC6 – MCP server for Cursor.** The service exposes an MCP server (stdio transport) with tools: `search_memories(query, filters, top_k)` and `list_sources()`. Cursor can connect to it via MCP config. The AI agent receives search results as structured tool responses. Verified: a PM can type a research question in Cursor chat and receive answers sourced from the mock OpenAI ChatGPT dataset.

- **AC7 – AI-synthesized summaries with references.** The MCP `search_memories` tool returns both raw results AND a synthesized summary. Synthesis is performed server-side: search results are passed to a configurable LLM (default: OpenAI GPT-4o-mini) which generates a readable answer with inline source citations. Response structure: `{ summary: string, references: [{title, url, source, type}], raw_results: [...] }`. The Cursor agent can present the summary directly or use `raw_results` for further analysis. Citations must correspond to real items in the search results. No hallucinated references. Degraded mode: returns raw results when LLM unavailable.

### Phase 2 — Quality & Polish

- **AC8 – Conversational research context.** The MCP `search_memories` tool accepts an optional `context` parameter (string) containing conversation history or prior findings. When provided, the tool uses this context to refine the vector search query (keyword expansion, filter adjustment, re-ranking). The Cursor agent manages conversation state; no server-side sessions. Verification: given "onboarding pain points" → then "which of those are from enterprise customers?" with context, returns enterprise-filtered results from the same topic.

- **AC9 – Error handling & empty states.** When search returns no results, the API returns an empty list with a descriptive message (not an error). When Qdrant or embedding provider is unavailable, operations degrade gracefully with clear error messages. LLM synthesis unavailable → raw results returned with degradation flag. Malformed inputs → clear error messages. Structured JSON logging throughout with configurable log level (default: INFO).

- **AC10 – Search quality evaluation.** A curated test set of 20+ queries with expected results (ground truth items from the mock dataset) exists under `tests/evaluation/`. An automated evaluation script measures precision@5 and recall against this test set. Results meet success metric: relevant items in top-5 for ≥ 80% of queries. The test set, evaluation script, and baseline results are committed to the repo.

- **AC11 – Configuration system.** `config.yaml` defines: embedding provider settings, Qdrant connection, LLM provider, logging level, and future connector configs. Config is validated on load. Sensitive values (API keys) sourced from environment variables. `config.yaml.example` with documented options provided.

### Phase 3 — Real Connectors

- **AC12 – Pluggable connector interface.** An abstract `BaseConnector` class defines the contract: `list_updated_items(since: datetime) -> list[NormalizedItem]` and `normalize_item(raw) -> NormalizedItem`. Adding a new data source requires only implementing this interface and adding a config entry.

- **AC13 – Monday.com connector.** Connects to Monday.com GraphQL API. Fetches items from configured boards. Maps configurable columns to `title`, `body`, and `metadata`. Supports incremental sync via `updated_at` filtering. Handles pagination and rate limits.

- **AC14 – Notion connector.** Connects to Notion API. Fetches pages from configured databases. Extracts full page content (blocks → plaintext). Supports incremental sync via `last_edited_time`. Handles pagination and rate limits.

- **AC15 – Cron-style sync engine.** `sync_all` orchestrates all connectors. For each item: computes `content_hash`; if new or changed, chunks and embeds; upserts to SQLite + Qdrant; if deleted, marks `is_deleted` and removes all chunks. Sync state (`last_synced_at`) persisted per source in a `sync_state` table. Idempotent — running twice with no changes produces no side effects. Replaces the seed script as the production data ingestion path.

### Phase 4 — Hardening

- **AC16 – First-sync batching & resilience.** First sync (no prior state) processes in batches of 100 items for large datasets. Connector failures are isolated (one fails, others continue). Auth errors (401/403) produce clear diagnostics identifying the failing source. Malformed items from source APIs are skipped and logged with item ID and error reason (never crash sync). Progress is resumable on interruption.

- **AC17 – Production observability.** All sync operations log: items fetched, changed, embedded, errors, and total duration. Search queries log: query text (truncated), filters, result count, and latency. Structured JSON format. Configurable log level. Errors include enough context (item ID, source, error type) for debugging without exposing sensitive data.

## NFRs / Constraints

- **Performance:** Search queries must return results in < 3 seconds for a corpus of up to 10,000 items. Sync of 1,000 items must complete in < 5 minutes.
- **Scalability:** Connector architecture must be pluggable — adding a new source (e.g., Jira, Linear, Slack, Google Docs) requires only implementing `BaseConnector` and config.
- **Security:** API keys and tokens are never stored in code or config files committed to git. All credentials via environment variables or secrets management. No source data is sent anywhere except to the configured embedding provider.
- **Reliability:** Sync failures for one connector must not block other connectors. Failed syncs are logged and retried on next run. Partial sync progress is not lost.
- **Cost awareness:** Embedding calls are minimized via `content_hash` diffing — unchanged items are never re-embedded. Batch embedding is used where supported.
- **Developer experience:** `docker-compose up` starts everything. Clear README with setup instructions. Config examples provided. Mock connectors enable development without live API access.
- **Open source friendly:** No proprietary dependencies. All core components (Qdrant, SQLite, FastAPI) are open source. Only the embedding provider requires a paid API key (OpenAI), and the interface allows swapping to free alternatives.
- **Observability:** All sync operations log: items fetched, items changed/new/deleted, items embedded, errors encountered, and total duration. Search queries log: query text (truncated), filters applied, result count, and latency. Logs use structured format (JSON) with configurable log level (default: INFO). Errors include enough context (item ID, source, error type) for debugging without exposing sensitive data.

## Test Strategy

### Phase 1 — Demo Slice
- **Unit tests:** Item model CRUD, content_hash computation, text chunking (split boundaries, overlap, parent_id linkage), embedding provider (mocked OpenAI responses), Qdrant client (mocked Qdrant).
- **Integration tests:** Seed script against Qdrant in Docker: load fixtures → verify SQLite + Qdrant state → search → verify ranked results with correct metadata. Full pipeline: seed → `search_memories` → verify response schema.
- **MCP tests:** MCP server with stdio client. Verify tool schemas, request/response format. Connect from Cursor and run a research query against seeded data.
- **Synthesis tests:** Verify summaries contain only citations from actual search results (no hallucinated references). Test degraded mode (LLM unavailable → raw results).
- **Demo testing (manual):** Configure Cursor MCP, seed the OpenAI ChatGPT dataset, ask 5+ research questions covering different types (feature requests, meeting notes, cross-topic). Verify synthesized answers are accurate, relevant, and citations link correctly.

### Phase 2 — Quality & Polish
- **Evaluation tests:** Run `tests/evaluation/evaluate.py` against curated test set. Verify precision@5 ≥ 80%. Iterate on chunking/embedding params if below threshold.
- **Error tests:** Empty queries, invalid filters, Qdrant down, LLM down — verify graceful degradation and clear messages.
- **Context tests:** Multi-turn queries with `context` parameter — verify refinement produces better/filtered results vs. standalone query.

### Phase 3 — Real Connectors
- **Connector tests:** Each connector tested with recorded API responses (VCR/cassette pattern or JSON fixtures). Verify pagination, rate-limit backoff, error handling (auth failure, malformed data). Live API tests gated behind `LIVE_API_TESTS=1` env flag.
- **Sync tests:** Full sync from both connectors → verify SQLite + Qdrant state → re-run → verify idempotency (no redundant operations). Test failure isolation (one connector errors, other succeeds).

### Phase 4 — Hardening
- **Batch tests:** Large dataset sync (1,000+ items). Interrupt and resume. Verify connector failure isolation.
- **Observability tests:** Verify log output format (JSON), content, and levels. Confirm error logs include debugging context.
