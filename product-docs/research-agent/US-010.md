# US-010: Research Agent – Clickable Evidence References in Chat

## Metadata
- **Repo**: `Product-OS-Research-Agent`
- **ID**: US-010
- **Status**: `done`
- **Branch**: `feature/US-010-clickable-evidence-refs` (merged to main)
- **Dependencies**: US-001 (core Research Agent), US-002 (canonical entity model), US-008 (pro researcher chat experience)

## Goal

Ensure that every evidence reference in Research Agent chat responses (e.g. “Bugs: Highlight reliability problems with the API [8, 17]”) is rendered as an obvious, clickable citation that cleanly maps to the underlying entities or documents, so product teams can immediately see what each reference points to and trust that key claims are backed by inspectable evidence.

## Target Users

- **Primary**: Product Managers using the Research Agent to run product research and generate structured insights (e.g. risks, opportunities, recommendations) that must be backed by inspectable evidence.
- **Secondary**: Product and engineering leaders reviewing high-level insights who occasionally need to drill into specific bugs, tickets, or feature requests to validate conclusions.

## Success Metrics

- **SM1 – Evidence inspection rate**: Among answers that include citations, ≥ 40% of sessions include at least one citation hover or click.
- **SM2 – Trust in answers**: In PM feedback prompts for answers with citations, ≥ 75% are rated "I trust this answer" or higher.
- **SM3 – Time-to-evidence**: In UX tests, median time to open a concrete supporting entity (bug, ticket, feature request) from a cited answer is ≤ 5 seconds.
- **SM4 – Evaluation coverage**: For at least one key scenario (e.g. “top product risks”), eval runs confirm that ≥ 90% of required claims have at least one correct citation attached.

## Value Proposition

By turning opaque numeric references into typed, clickable citation chips with rich previews and deep links, product teams can move from "trusting the model" to "trusting the evidence": they can verify claims in a few seconds, reuse the same entities in follow-up work (tickets, PRDs, experiments), and feel confident that Research Agent’s recommendations are grounded in real bugs, tickets, and requests rather than opaque model output.

## Problem Statement

Today, Research Agent chat answers can mention entities and then append opaque numeric references (e.g. “Bugs: Highlight reliability problems with the API [8, 17]”) without any UI affordance that explains what those numbers are or how they map to concrete bugs, feature requests, or tickets. Users cannot hover to see a summary, click to open the underlying record, or easily cross-check which specific entities support a given claim. This breaks the “pro product researcher” expectation from US-008: PMs see polished, structured answers but have no fast, trustworthy way to inspect the evidence behind each statement, which reduces trust in the agent’s conclusions and makes follow-up investigation unnecessarily slow.

## Non-Goals

- Change how retrieval or ranking chooses which entities to cite; this story assumes the upstream research pipeline already selects reasonable supporting entities.
- Introduce new entity types or external tools; we only expose citations for entities and integrations that already exist (e.g. Bugs, Support Tickets, Feature Requests, Docs).
- Redesign the entire chat UI layout beyond what is required to add inline chips and a sources/evidence panel.
- Implement full-blown document viewers; we will show concise snippets in-product and deep-link to the external system for full detail.
- Change evaluation metrics or the questions suite beyond what is needed to add citation-aware checks.

## Acceptance Criteria

AC1 – Inline typed citation chips  
- Within any structured answer section (e.g. TL;DR, Key Insights, Evidence / Data Sources), when the model references specific entities, the UI renders **typed citation chips** instead of bare numeric brackets.  
- Each chip shows a short typed ID such as `BUG-8`, `BUG-17`, `FR-3`, `SUP-2`, or a similar compact form derived from the entity type and an answer-local index.  
- Chips are visually distinct (pill or badge style) and consistently placed immediately after the text they support (on the same line or directly below), so it is obvious what claim they are attached to.

AC2 – Hover previews with entity context (V1 requirement)  
- Hovering (or long-press on touch) over a citation chip opens a small popover that shows at least: entity type, human-readable title/summary, one short snippet (e.g. first sentence of description or most relevant comment), and key metadata such as status/severity where available.  
- The snippet clearly reflects why this entity is relevant to the preceding claim (e.g. includes “504 timeout on large token contexts” for the reliability example).  
- The popover appears within ≤300ms for cached entities and degrades gracefully (spinner + “Loading…” state) when data is not yet loaded, without blocking the main answer.

AC3 – Click-through deep links to external systems  
- Clicking a citation chip (or a dedicated “Open” affordance in the popover) navigates to a deep link for the underlying record: either an in-app entity drawer or the external system (e.g. Monday/Jira/Intercom) depending on existing integration behavior.  
- For entities that have both an internal canonical view and an external system URL, the primary click behavior is defined and consistent (e.g. in-app drawer first with a secondary “Open in Monday” link).  
- If a deep link is unavailable (e.g. entity has been deleted), the UI surfaces a clear, non-breaking message in the popover instead of silently failing or doing nothing.

AC4 – Sources / Evidence panel aligned with chips  
- Each answer that includes citations also shows a `Sources` or `Evidence` section (footer or side panel) listing all referenced entities grouped by type (Bugs, Support, Feature Requests, Docs, etc.).  
- The list reuses the **same typed IDs** as the inline chips (e.g. `BUG-8`, `BUG-17`) so users can trivially map between inline claims and the sources list.  
- Clicking an item in the Sources list scrolls/highlights the corresponding chip in the answer (or vice versa), ensuring there is a single, unambiguous mapping for every reference.

AC5 – Model and orchestration behavior for citations  
- The orchestration layer maintains a per-answer citation store that assigns stable, answer-local typed IDs and exposes these to both the renderer and evaluation harness.  
- The LLM is instructed to only reference citation IDs that actually exist in the citation store; there is no way for it to fabricate `BUG-999` without a backing entity.  
- For long answers, the system prefers a small number of high-quality citations per claim (1–3) rather than attaching every retrieved entity; this keeps the UI readable while still auditable.

AC6 – Backward compatibility and failure modes  
- Answers that do not contain any citations continue to render as today, with no visual regressions.  
- If the citation store is empty or the retrieval step fails, the renderer does not show dangling chips or Sources sections; instead, the model falls back to non-cited text and, where appropriate, the agent explicitly notes that it cannot currently reference specific entities.  
- If loading hover content fails (API error, timeout) or the entity is missing/permission-denied, the popover shows a clear message such as “Could not load details for BUG-8 right now” and the rest of the answer remains fully usable.  
- If a deep link cannot be opened, the click is a no-op accompanied by inline feedback rather than navigating to a broken page.

## NFRs / Constraints

- **NFR1 – Latency for hover previews**  
  - For entities already present in the conversation context, hover previews must appear with p95 ≤ 300ms.  
  - For entities requiring an API fetch, p95 ≤ 1s with a visible loading state; failure must not block other interaction.

- **NFR2 – Evaluationability**  
  - The citation store and typed IDs are exposed to the eval harness so we can test, for a given answer, that referenced entities actually exist and plausibly support the claims they cite.  
  - At least one eval scenario from `questions.md` / `reference_answers.md` is updated to check for the presence and correctness of citations (e.g. that the “top risks” answer references the expected bugs and requests).

- **NFR3 – Accessibility & keyboard support**  
  - Citation chips are focusable via keyboard and the hover preview can be opened via focus or keyboard action, with screen-reader labels that describe the entity type, title, and status.  
  - The Sources/Evidence list is screen-reader friendly and preserves the mapping between inline chips and list entries.

- **NFR4 – Visual consistency**  
  - Citation chips and Sources/Evidence styling follow the existing Research Agent design system (colors, typography, spacing) and do not introduce entirely new primitive styles.  
  - The new UI scales reasonably for answers with up to dozens of citations without overwhelming the layout (e.g. chips wrap nicely, Sources list scrolls independently if long).

- **NFR5 – Security / permissions**  
  - Citation previews and deep links respect existing entity permissions; users never see snippets from entities they are not allowed to access, and clicks to external systems use the same auth mechanisms as existing deep links.
  - Telemetry for citation usage (hover, click, error events) is captured so Success Metrics SM1–SM3 can be measured without additional instrumentation work.

## Dev Tasks

1. **Design citation chips and Sources/Evidence UX**  
   - Produce UX mocks for inline typed citation chips, hover previews (including loading/error states), and the Sources/Evidence panel, following preferences from US-010 (typed IDs, hover snippet as V1 requirement, click-through deep links).

2. **Implement citation store and typed ID assignment in backend/orchestration**  
   - Introduce a per-answer citation store that normalizes retrieved entities into a common shape and assigns answer-local typed IDs (e.g. `BUG-1`, `BUG-2`, `FR-1`).  
   - Expose this store to the renderer and eval harness; update the prompt/agent behavior so the LLM can reference these IDs reliably.

3. **Render inline citation chips with hover previews**  
   - Update the chat message renderer to detect citation references in the model output and replace them with chip components wired to the citation store.  
   - Implement the hover/long-press preview popover, including snippet display, metadata, loading state, and error handling.

4. **Implement Sources/Evidence section and chip synchronization**  
   - Add a per-answer Sources/Evidence section that lists all citations by typed ID and entity type.  
   - Wire interactions so clicking an item in the list scrolls/highlights the matching chip, and vice versa.

5. **Wire deep-link navigation and permission checks**  
   - Ensure each citation has a deterministic primary click behavior (drawer vs external link) and that permission checks are enforced before showing previews or following links.  
   - Add logging/telemetry for citation usage (hover, click, errors) to inform future improvements.

6. **Update evals and reference answers for citation coverage**  
   - Extend at least one scenario in `questions.md` / `reference_answers.md` (e.g. “top product risks”) to include expected citations and use the new citation store in the eval harness to verify correctness.

## Test Strategy

1. **TS1 – UX walkthroughs for cited answers**  
   - Manually test representative answers (e.g. “top product risks”, “what are our biggest reliability issues”) to confirm inline chips render correctly, hover previews show the right entities, and deep links open the expected external records.

2. **TS2 – Edge cases & failure modes**  
   - Simulate missing entities, permission-denied responses, and API failures for preview/deep-link calls to verify that chips degrade gracefully with clear messaging and no layout breakage.

3. **TS3 – Accessibility checks**  
   - Verify keyboard navigation and screen-reader announcements for chips and the Sources/Evidence list, ensuring that users can understand which sources back which claims without relying solely on visual cues.

4. **TS4 – Evaluation integration**  
   - Run the updated eval suite to confirm that citation-aware scenarios pass and that answers without citations are unaffected by the new machinery.
