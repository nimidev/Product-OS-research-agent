# US-007: Entity and Field Mapping for Integrations (Connect → Map → Sync)

## Metadata
- **Repo**: `Product-OS-Research-Agent`
- **ID**: US-007
- **Status**: `create`
- **Branch**: (not yet created)
- **Dependencies**: US-003 (Phase 1 Monday.com integration) provides the foundation; this story extends it with guided mapping UX.

## Goal

Ensure that during the integration process we deliver not only a technical implementation of the integration but **always** the mapping of Product OS entities to the relevant integration entities and fields. Users (e.g. PMs) should be able to: connect a tool (e.g. Monday), choose which Product OS entities to sync (Epics, Tasks, Bugs, Support tickets), link each entity to the right board, map fields (Product OS ↔ integration), set sync direction (two-way vs one-way), and review/test before activating.

## Target Users & Value

- **Primary user**: Admin / ops owner responsible for configuring and maintaining integrations (starting with Monday.com).
- **Secondary beneficiaries**: PMs and product teams who consume synced Product OS entities (epics, tasks, bugs, support tickets) in search and context panels.

**Value Proposition**

- After completing an integration, admins can *see and trust* that real tool data is flowing into Product OS via explicit, validated mappings instead of a “connected but empty” state.
- Product teams get searchable Product OS entities backed by real Monday boards without manual, out-of-band mapping work.

## Success Metrics

- **Ingestion coverage**: For at least one mapped Monday board per entity type (Epics, Tasks), ≥90% of active items appear as Product OS entities after an initial sync.
- **Search grounding**: Queries about mapped epics/tasks return Monday-backed entities in `/search_memories` with citations to Monday URLs.
- **Setup completion**: A strong majority of admins who start the Monday mapping wizard can complete the flow (connect → choose entities → link boards → map fields → test → activate) without requiring manual DB/CLI intervention in their first session.

## Problem Statement

Today, completing an integration “connect” flow (e.g., Monday.com) does **not** result in a concrete, validated mapping between Product OS entities and the external system. Admins/ops can flip an integration to “enabled”, but there is no guided, enforced step where they: choose which Product OS entities participate, link them to specific boards/projects, map fields explicitly, and verify that real data flows through those mappings. As a result, even after a “successful” connection, nothing meaningful happens: sync either pulls nothing, pulls from the wrong place, or the UX to configure mappings is so broken (e.g., Monday boards/columns not surfacing correctly) that users cannot complete setup or trust the data.

## Non-Goals

- Fully general visual mapping for **all** future integrations (this story establishes the pattern and validates it against Monday; other tools can adopt it later).
- Complex transformation logic (e.g., arbitrary formulas, multi-step pipelines); focus is on 1:1 and simple enum/status mappings.
- Advanced conflict-resolution semantics (last-writer-wins policies, per-field merge rules, etc.).
- Board discovery and permissions UX in Monday itself (we assume the API token / OAuth has sufficient access to the chosen boards).
- Automated creation of boards/columns in Monday; we assume boards/columns already exist and are selected/mapped in Product OS.

## Acceptance Criteria

**AC1 – Mapping as a first-class step after connect**  
After an admin connects Monday, they are guided into a dedicated “Configure mapping” flow where they must:  
- Choose which Product OS entities to sync (at least Epics, Tasks, Bugs, Support tickets for Monday), and  
- Link each chosen entity to one or more Monday boards before the integration can be marked “active”.

**AC2 – Field-level mapping UX with real Monday schema**  
For each entity–board pair, the mapping UI surfaces **real Monday columns** for that board (fetched via the Monday API) and allows the admin to map core Product OS fields (e.g., Title, Description, Status, Owner, Parent Epic, Severity, Priority, Customer, Tags) to specific Monday columns. The admin can save a mapping only when required fields for that entity have been mapped.

**AC3 – Directionality per entity type**  
Admins can set sync direction per entity type (at least for Monday):  
- Epics, Tasks: two-way (changes propagate Monday ↔ Product OS).  
- Bugs, Support tickets: Monday → Product OS only.  
The selected direction is persisted in integration config and respected by the sync engine.

**AC4 – Verified ingestion from a mapped Monday board**  
Given a valid Monday token and at least one mapped board for Epics and Tasks, after running the sync command (or scheduled sync), entities from that board appear in Product OS as the correct canonical types (e.g. Epics and Tasks) and are:  
- Visible in the canonical store (entities table with `source_system = monday`), and  
- Discoverable via the Product OS search client (e.g. `/search_memories`) with citations pointing back to the Monday items.

**AC5 – Validation/test step in the UX**  
From the mapping screen, an admin can trigger a “Test sync” for a given entity/board (e.g. “Test Epic sync”), which:  
- Fetches a small sample of items from the mapped Monday board,  
- Shows how each will map into Product OS fields (including status mappings), and  
- Only allows activating the mapping when the test call succeeds and returns at least one item.

**AC6 – Integration-agnostic design with Monday as reference implementation**  
The mapping model and API surface (config shape, storage model) are integration-agnostic, so additional tools (e.g., Jira, Notion) can plug into the same pattern later. For this story, Monday is the only integration required to fully implement, validate, and demonstrate the end-to-end behavior.

## NFRs / Constraints

- **Reliability**: Mapping config is persisted server-side (DB) and is versioned/updated atomically so partially-saved mappings do not leave the integration in a broken state.
- **Safety**: Two-way mappings must not overwrite data silently; at minimum, we document direction semantics and ensure one-way mappings never push changes back to Monday.
- **Performance**: Test sync for a single entity/board returns a preview within a few seconds for typical board sizes (e.g. ≤ 200 items), or clearly indicates when a board is too large and sampling is applied.
- **Discoverability**: At any time, an admin can inspect the current mapping for a given integration (which entities, which boards, which fields, and directions) from the Integration settings UI.
- **Security & scopes**: Mapping and sync use the minimal Monday scopes required (e.g. read-only for Monday → Product OS flows; write scopes only when two-way sync is enabled). API tokens/OAuth credentials are stored only in backend config storage, never logged, and not exposed to the client beyond “connected” status.

## Edge Cases & Error Handling

- **Invalid or expired Monday token** → clear error in mapping UI with CTA to re-authenticate or update the token; mappings are not activated until token is valid.
- **No accessible boards or columns for a selected entity** → explain the issue and block activation until at least one board and required columns are available.
- **Required Product OS fields not mapped** → mapping cannot be saved; missing fields are highlighted inline in the UI.
- **Large boards in preview** → for very large boards, test preview samples a subset of items and indicates that sampling is applied.
- **User cancels mid-flow** → integration may remain “connected but not configured”; it does not participate in sync until mappings are completed, tested, and explicitly activated.

## Dependencies & Integration

- Relies on the existing `python -m research_agent sync` (or equivalent scheduled runner) to execute mappings and ingest data.
- Extends the existing Monday connector and integration config shape to support per-entity board/field mappings and directionality.
- Does not introduce a new scheduler; it plugs into the existing sync pipeline and `integration_configs` storage model.

## Reference: Concrete Monday Example (Epics, Tasks, Bugs, Support)

*Example flow for a PM named Dana.*

1. **Connect Monday**  
   Click “Connect Monday” in Product OS → OAuth flow completes → back in Product OS with Monday connected.

2. **Choose entities**  
   Dana selects: Epics, Tasks, Bugs, Support tickets.

3. **Link entities to boards**  
   - Epics → “Product Epics” board  
   - Tasks → “Engineering Tasks” board  
   - Bugs → “Bug Inbox” board  
   - Support tickets → “Customer Support” board  

4. **Map fields**  
   - **Epics** (Product OS ↔ “Product Epics”): Title ↔ Item name, Description ↔ “Details” (long text), Owner ↔ “Epic owner” (People), Status ↔ “Epic status”, Tags ↔ “Tags”.  
   - **Tasks** (↔ “Engineering Tasks”): Title ↔ Item name, Parent Epic ↔ “Epic link” (Connect boards), Status ↔ “Task status”, Assignee ↔ “Owner”.  
   - **Bugs** (↔ “Bug Inbox”): Title ↔ Item name, Severity ↔ “Severity”, Source ↔ “Source” (Dropdown), Status ↔ “Bug status”.  
   - **Support tickets** (↔ “Customer Support”): Title ↔ Item name, Customer ↔ “Customer”, Priority ↔ “Priority”, Status ↔ “Ticket status”.

5. **Set directions**  
   Epics & Tasks: two-way. Bugs & Support tickets: Monday → Product OS only.

6. **Review & Test**  
   “Test Epic sync” shows sample Monday epics and how they’ll look in Product OS (e.g. status mapping “Working on it” → In Progress, “Done” → Done). Dana approves and activates.

## UX Principles to Build In

- **Object-first, not tool-first**: Lead with Product OS entities, then ask “Where are these in [Monday]?” so Product OS feels like the source of truth.
- **Opinionated defaults, but editable**: Auto-suggest board and field mappings (e.g. item name → Title, Status → Status); let power users refine.
- **Separation of “connect” vs “configure”**: Connection (OAuth) is a quick success moment; mapping is a clearly separate, guided step.
- **Progressive complexity**: Show minimal required mappings first (Title, Status, Owner); advanced mappings (tags, custom fields, cross-board links) behind “Advanced mapping” toggle.

## Dev Tasks

1. **Extend Monday integration config to store mappings**
   - Extend the existing Monday integration config model to store per-entity mappings: entities ↔ board IDs, field mappings, and directionality.
   - Expose this mapping via backend APIs (e.g. extend `/integrations/monday` or add dedicated mapping endpoints) so the UI can read/write the full configuration.

2. **Fetch Monday schema (boards + columns) for mapping UI**
   - Backend: add a small service to call the Monday API and list boards and their columns, given the configured token.
   - Frontend: in the wizard, allow admins to link Product OS entities (Epics, Tasks, Bugs, Support tickets) to specific boards and select columns for each required Product OS field.

3. **Implement per-entity directionality in sync**
   - Extend `_build_connectors` and related sync logic so connectors honor per-entity direction settings (two-way vs Monday → Product OS).
   - Ensure one-way mappings never write back to Monday, and document/implement clear semantics for two-way flows.

4. **Implement “Test sync” preview endpoint + UI**
   - Backend: create an endpoint that, for a given entity/board mapping, fetches a small sample of Monday items and returns how they map into Product OS fields (including status mapping examples).
   - Frontend: add a preview in the wizard (“Test Epic sync” style) that shows sample records and their mapped fields, with clear error messages on failure.

5. **Wire mappings into full sync path**
   - Use stored mappings when constructing Monday connectors so sync reads from the correct boards and populates Product OS entities with mapped fields and correct `source_system` / `entity_type`.
   - Verify that entities from mapped boards appear in the canonical store and are included in `/search_memories` responses with citations pointing back to Monday items.

6. **Audit and remove mock-only behavior when Monday is mapped**
   - Ensure that once Monday integration is configured with mappings, chat/search no longer rely on static mock “Monday” entities.
   - Keep mock behavior only for cases where no real integration is configured, with clear degradation messaging in the UI.

## Test Strategy

- **Unit tests**
  - Mapping model read/write (including directionality) in the backend integration config layer.
  - Monday schema fetch (boards/columns) and mapping resolution logic for entity ↔ board/field mappings.
  - Connector-building and sync logic honoring per-entity direction (two-way vs Monday → Product OS).

- **Integration tests**
  - With a test Monday account/fixture: configure mappings, run sync, and assert that entities in the DB have `source_system = monday`, the expected `entity_type`, and mapped fields populated.
  - Verify that `/integrations/monday/test` and the “Test sync” preview endpoint return sample items and mapped fields, and surface errors for invalid tokens, missing scopes, or inaccessible boards.

- **UI tests (manual or automated)**
  - End-to-end wizard: connect Monday/API token, choose entities, link boards, map fields, run “Test sync”, and activate, ensuring validation prevents incomplete mappings.
  - Error flows: invalid/expired token, no boards returned, missing required columns, failing preview call, and user cancel mid-flow.

- **Regression checks**
  - Existing seed-only/mock flows continue to work when Monday is not configured.
  - Adding Monday mappings does not regress other integrations or the base sync pipeline.
