# US-002: Migrate to Canonical Entity Model

## Metadata

- **Repo**: `Product-OS-Research-Agent`
- **ID**: US-002
- **Status**: `create`
- **Branch**: `feature/US-002-canonical-entities`
- **Dependencies**: US-001 (builds on same repo; replaces Item/sync/search implementation with canonical model)

## Goal

Migrate from the current flat schema (title, body, metadata) to a **canonical entity model** with config-driven field mappings, enabling field-aware search and preserving rich semantics from source systems (Monday.com, Notion, future Jira/Gong). **Re-ingest strategy:** no backward compatibility; replace schema and re-ingest from `data/` (mock) and re-sync from sources (live). **Flexible search UX:** the user can ask any question; the system determines which entities (and optionally fields) to search based on the question and its context. Easy extensibility for new tools/entities via config.

## Problem Statement

The current implementation uses a simple flat schema that works for basic Monday.com + Notion sync but loses rich field semantics (e.g., Monday "pain_points" column gets dumped into unstructured `body`). PMs cannot search by field (e.g., "pain_points" across feature_requests). Adding new sources (Jira, Gong, Zoom) would require code changes per tool. A canonical entity model with config-driven mappings will preserve field semantics, enable field-aware search, and let orgs define their own tool→canonical mappings without code changes.

## Target Users

Product managers and teams using the Research Agent to search organizational knowledge; operators who configure Monday/Notion (and future) connectors via YAML.

## Non-Goals

- Backward compatibility with the existing Item table or old APIs (re-ingest only; clean break).
- Real-time webhooks or new connectors beyond the existing Monday/Notion (Jira/Gong are future; this story establishes the pattern).
- Changing MCP tool surface for Cursor (existing `search_memories` can be updated in-place to new schema; v2 search params additive).

## Success Metrics

- All mock data in `data/fixtures/` re-ingests into new schema via seed (no migration script).
- Configurable field mapping works (e.g., Monday "text5" → canonical "pain_points").
- **Flexible search:** The user can ask any question without specifying which entities to search. The system determines which entity types (and optionally which fields) to search based on the actual question and its context — e.g. "what bugs were reported about login?" may narrow to bugs; "insights related to a problem statement" may span meetings, feature requests, PRDs. When inference suggests a narrow scope, search uses it for precision; when the question is broad or ambiguous, search runs across all entities. No rigid query format required.
- Search supports optional filters (`entity_types`, `field_names`); when omitted or empty, search runs across all entity types and all searchable fields unless query/context understanding infers a narrower scope.
- New connectors (e.g., Jira, Gong) can follow the same pattern via config with minimal code.

## Canonical Model (Reference)

**6 core entity types + canonical fields (exact):**

| Entity           | Canonical Fields                                                                 |
|------------------|-----------------------------------------------------------------------------------|
| Feature Request  | title, description, customer, priority, status, votes                            |
| Roadmap Item     | title, description, target_start, target_end, status, priority                   |
| Support Ticket   | title, description, customer, priority, status, resolution                      |
| Bug              | title, description, severity, status, affected_version, priority                 |
| PRD              | title, overview, target_users, requirements, success_metrics, status               |
| Meeting Note     | title, transcript, summary, attendees, date, tags                                  |

**Storage (3 tables):**

1. **entities**: entity_type, source_system, source_id, title, timestamps (created_at, updated_at, etc.)
2. **entity_fields**: entity_id, field_name (e.g. "pain_points"), field_type (e.g. "text"), field_value
3. **chunks**: entity_id, field_name, text (for embeddings); supports field-scoped search

## Architecture Direction

- **Schema replacement (no migration):** Replace Item table with `entities` + `entity_fields` + `chunks`. Drop old schema; seed and sync write only to new schema. Mock data in `data/fixtures/` updated to canonical field structure and re-ingested; live data re-synced from Monday/Notion after deploy.
- **Connector pattern:** Generic interface: `list_changed_items(since)`, `normalize(raw_item, mapping_config) → (Entity, [EntityField], [Chunk])`. Config-driven mapping (YAML) per source/entity.
- **Search:** `search_memories(query, entity_types=[], field_names=[], filters={}, context=?)` (signature can include optional context). Search UX is **flexible:** the system determines which entities (and optionally fields) to search based on the user's question and context — e.g. query understanding infers relevant entity_types/field_names when the question implies scope ("bugs about X" → bug; "insights on problem statement" → meeting_note, feature_request, prd). When no scope is inferred or question is broad, search runs across all entity types and searchable fields. Caller (e.g. MCP/Cursor agent) or service may perform the inference; filters passed to search reflect the chosen scope. Vector payload includes entity_type, field_name, metadata.

## Acceptance Criteria

- **AC1** – New schema only. Tables `entities`, `entity_fields`, `chunks` exist; Item table (and old schema) removed. Seed and sync write only to new schema.
- **AC2** – Mock fixtures aligned to canonical fields. Seed loads these into entities + entity_fields + chunks.
- **AC3** – Feature requests (mock or Monday) appear as feature_request entity with mapped fields (e.g. pain_points or description) in entity_fields.
- **AC4** – Meeting notes (mock or Notion) appear as meeting_note entity with transcript (or mapped) field in entity_fields.
- **AC5** – Field-aware search: `search("slow search", entity_types=["meeting_note"], field_names=["transcript"])` returns results from transcript chunks only.
- **AC6** – Config-driven mapping: changing mapping (e.g. text5 → workarounds) and re-syncing allows search to find content in that field.
- **AC7** – `sync_all` and search endpoints work with new schema; no dual-write or legacy code paths.
- **AC8** – Docker-compose runs with new schema; single seed run populates from fixtures.
- **AC9** – README explains how to add a Monday board mapping (config-driven).
- **AC10** – All six entity types (feature_request, roadmap_item, support_ticket, bug, prd, meeting_note) can be ingested from fixtures or connectors and returned by search when filtered by `entity_types`.
- **AC11** – Intuitive search default: when the user (or MCP caller) does not pass `entity_types` or `field_names` (or passes empty lists), search is performed across all entity types and all searchable fields unless query/context inference narrows scope. A natural-language query such as "Give me all insights related to a problem statement" must return relevant results from meetings, feature requests, PRDs, etc., without the user specifying which entities to search.
- **AC12** – Flexible search: the system is able to determine which entities (and optionally which fields) to search based on the user's actual question and context. The user can ask any question (e.g. "what bugs were reported about login?", "customer pain points from last quarter", "decisions from standups about pricing"); the system infers appropriate entity scope when the question implies it (e.g. bugs → entity_types=["bug"]; broad "insights" → search all). Implementation may live in the Research Agent (query understanding before calling search) or in the MCP/caller layer; search accepts the resulting entity_types/field_names. No fixed query format or required filters for the end user.

## NFRs / Constraints

- **Re-ingest only:** No migration script. Data loss for in-DB state is acceptable; mock data re-ingested from fixtures, live data re-synced from sources after deploy.
- **Config-driven:** YAML mappings for any org's Monday/Jira/Notion schemas; no hardcoded column names for org-specific fields.
- **Extensibility:** New tools/entities via config + minimal code (generic connector pattern).

## Edge Cases & Error Handling

- **Empty search:** Returns empty list with no error (consistent with existing behavior).
- **Malformed fixture:** Seed logs error for the row, skips it, continues (no crash).
- **Invalid mapping config:** Sync/seed fails fast with clear error (e.g. "Unknown field in mapping: X").
- **Connector failure (Monday/Notion):** Isolated per connector; other sources continue; failed source logged and retried next run.
- **Query/context inference unavailable:** When query/context inference cannot determine scope (e.g. ambiguous question or inference unavailable), search falls back to all entity types and searchable fields.

## Test Strategy

- Seed tests: load canonical-shaped fixtures → entities + entity_fields + chunks populated; idempotent re-run.
- Field-aware search tests: entity_types + field_names filters return correct chunks.
- Default search tests: query with no entity_types/field_names returns results from multiple entity types (e.g. meeting_note, feature_request, prd) when content matches.
- Flexible search tests: for questions that imply scope (e.g. "bugs about login", "meeting notes about roadmap"), results are appropriately scoped (by inference in service or caller); for broad questions ("all insights on X"), results span relevant entity types.
- Config change tests: remap field in YAML, re-sync/seed, search finds content in that field.
- Sync + search integration tests against new schema only.
