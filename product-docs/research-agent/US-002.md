# US-002: Migrate to Canonical Entity Model

## Metadata

- **Repo**: `Product-OS-Research-Agent`
- **ID**: US-002
- **Status**: `create`
- **Branch**: (not yet created)
- **Dependencies**: US-001 (builds on same repo; replaces Item/sync/search implementation with canonical model)

## Goal

Migrate from the current flat schema (title, body, metadata) to a **canonical entity model** with config-driven field mappings, enabling field-aware search and preserving rich semantics from source systems (Monday.com, Notion, future Jira/Gong). **Re-ingest strategy:** no backward compatibility; replace schema and re-ingest from `data/` (mock) and re-sync from sources (live). Easy extensibility for new tools/entities via config.

## Problem Statement

The current implementation uses a simple flat schema that works for basic Monday.com + Notion sync but loses rich field semantics (e.g., Monday "pain_points" column gets dumped into unstructured `body`). PMs cannot search by field (e.g., "pain_points" across feature_requests). Adding new sources (Jira, Gong, Zoom) would require code changes per tool. A canonical entity model with config-driven mappings will preserve field semantics, enable field-aware search, and let orgs define their own tool→canonical mappings without code changes.

## Non-Goals

- Backward compatibility with the existing Item table or old APIs (re-ingest only; clean break).
- Real-time webhooks or new connectors beyond the existing Monday/Notion (Jira/Gong are future; this story establishes the pattern).
- Changing MCP tool surface for Cursor (existing `search_memories` can be updated in-place to new schema; v2 search params additive).

## Success Metrics

- All mock data in `data/fixtures/` re-ingests into new schema via seed (no migration script).
- Configurable field mapping works (e.g., Monday "text5" → canonical "pain_points").
- Search supports `entity_types=["meeting_note"]` and `field_names=["transcript"]`.
- New connectors (e.g., Jira, Gong) can follow the same pattern via config with minimal code.

## Canonical Model (Reference)

**6 core entity types + canonical fields (exact):**

| Entity           | Canonical Fields                                                                 |
|------------------|-----------------------------------------------------------------------------------|
| Feature Request  | title, description, customer, priority, status, votes                            |
| Roadmap Item     | title, description, target_start, target_end, status, priority                   |
| Support Ticket   | title, description, customer, priority, status, resolution                      |
| Bug              | title, description, severity, status, affected_version, priority                 |
| PRD              | title, overview, target_users, requirements, success_metrics, status               |
| Meeting Note     | title, transcript, summary, attendees, date, tags                                  |

**Storage (3 tables):**

1. **entities**: entity_type, source_system, source_id, title, timestamps (created_at, updated_at, etc.)
2. **entity_fields**: entity_id, field_name (e.g. "pain_points"), field_type (e.g. "text"), field_value
3. **chunks**: entity_id, field_name, text (for embeddings); supports field-scoped search

---

## Architecture Direction

- **Schema replacement (no migration):** Replace Item table with `entities` + `entity_fields` + `chunks`. Drop old schema; seed and sync write only to new schema. Mock data in `data/fixtures/` updated to canonical field structure and re-ingested; live data re-synced from Monday/Notion after deploy.
- **Connector pattern:** Generic interface: `list_changed_items(since)`, `normalize(raw_item, mapping_config) → (Entity, [EntityField], [Chunk])`. Config-driven mapping (YAML) per source/entity.
- **Search:** `search_memories(query, entity_types=[], field_names=[], filters={})` (can replace or extend current signature); vector payload includes entity_type, field_name, metadata.

## Acceptance Criteria

- **AC1** – New schema only. Tables `entities`, `entity_fields`, `chunks` exist; Item table (and old schema) removed. Seed and sync write only to new schema.
- **AC2** – Mock fixtures aligned to canonical fields. Fixtures in `data/fixtures/` use canonical field names per entity type (e.g. feature_request: title, description, customer, priority, status, votes; meeting_note: title, transcript, summary, attendees, date, tags). Seed loads these into entities + entity_fields + chunks.
- **AC3** – Feature requests (mock or Monday) appear as feature_request entity with mapped fields (e.g. pain_points or description) in entity_fields.
- **AC4** – Meeting notes (mock or Notion) appear as meeting_note entity with transcript (or mapped) field in entity_fields.
- **AC5** – Field-aware search: `search("slow search", entity_types=["meeting_note"], field_names=["transcript"])` returns results from transcript chunks only.
- **AC6** – Config-driven mapping: changing mapping (e.g. text5 → workarounds) and re-syncing allows search to find content in that field.
- **AC7** – `sync_all` and search endpoints work with new schema; no dual-write or legacy code paths.
- **AC8** – Docker-compose runs with new schema; single seed run populates from fixtures.
- **AC9** – README explains how to add a Monday board mapping (config-driven).

## NFRs / Constraints

- **Re-ingest only:** No migration script. Data loss for in-DB state is acceptable; mock data re-ingested from fixtures, live data re-synced from sources after deploy.
- **Config-driven:** YAML mappings for any org's Monday/Jira/Notion schemas; no hardcoded column names for org-specific fields.
- **Extensibility:** New tools/entities via config + minimal code (generic connector pattern).
