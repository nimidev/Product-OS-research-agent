# US-009: Integrations Page – View vs Edit UX Redesign

## Metadata
- **Repo**: `Product-OS-Research-Agent`
- **ID**: US-009
- **Status**: `done`
- **Branch**: `feature/US-009-integrations-view-edit-ux` (merged to main)
- **Dependencies**: (none identified yet)

## Goal

Redesign the Integrations page experience so that users have clear visibility into which integrations are enabled, which entities are configured for each integration (e.g. Support, Bugs, Feature Requests), and how their fields are mapped, with a clean separation between read-only “View” mode and a guided “Edit” mode for configuring entities and field mappings.

## Target Users

- **Primary**: Product Managers configuring Product OS integrations so the Research Agent has the right product entities available.
- **Secondary**: IT / admin users responsible for connecting external tools (e.g. Monday.com) and maintaining integration health.

## Value Proposition

By making integrations configuration visible, safe, and predictable (clear View vs Edit modes, full entity coverage, and simple mapping summaries), PMs and IT can confidently complete integrations and audit which entities are feeding the Research Agent, without fear of accidentally changing live mappings.

## Problem Statement

Product managers and IT admins configuring Product OS need a reliable way to (1) see which integrations are connected, (2) understand which entities are actually configured for each integration (e.g. Support, Bugs, Feature Requests), and (3) trust that the right fields are mapped so the Research Agent has complete context. Today, the Integrations experience blends read-only visibility with configuration in a single surface: entity selection happens via ambiguous “bubbles”, only a subset of configured entities are visible at a glance (e.g. Monday showing just Support Tickets while Bugs and Feature Requests exist), and the same UI is used both to inspect current mappings and to change them. This makes it hard to audit coverage, easy to miss partially-configured entities, and risky to click into mappings because the user is never sure whether they are “just looking” or actively editing a live integration.

## Non-Goals

- Change the underlying integration model, data structures, or existing Monday.com integration behavior.
- Add new third-party integrations or new entity types beyond what already exists.
- Redesign the detailed field-mapping UI itself beyond minor layout adjustments needed to embed it into the new flows.
- Implement new sync semantics, directions, or schedules; this story only surfaces and clarifies what already exists.
- Build a fully responsive/mobile-specific experience; desktop/web is the primary target (mobile should remain usable but not pixel-perfect).

## Acceptance Criteria

## Success Metrics

- **SM1 – Auditability**: In UX tests, ≥80% of PM/IT users can, within 60 seconds, correctly answer: "Which entities are active for Monday, and are any needing attention?"
- **SM2 – Configuration confidence**: In UX tests, ≥80% of users report they are "confident" or "very confident" they did not accidentally change a live integration when only viewing it.
- **SM3 – Flow completion**: For a new integration setup task, ≥70% of users can complete Entities + Field mappings + Review in under 10 minutes without facilitator intervention.

AC1 – Top-level integrations overview  
- A user can open `/integrations` and see, for each integration, a row or card that clearly shows: integration name and logo, connection status (e.g. Connected / Not Connected), number of configured entities (e.g. `3 entities enabled`), and last sync timestamp or badge.  
- From this list, the user can click an integration and land on a dedicated detail page (View mode) without entering any editing state.

AC2 – Integration detail – View mode  
- On `/integrations/{integration}`, the user sees a non-editable “View mode” that lists **all** entities available for that integration (including disabled / not configured ones) with per-entity status chips such as `Enabled`, `Configured but disabled`, or `Not configured`.  
- For each entity, the user sees a short summary showing only the number of mapped fields (e.g. `8 fields mapped`); this data reflects the existing mapping configuration with no additional data model changes.  
- Clicking an entity opens a read-only mapping view (drawer, panel, or section) that reuses the existing field-mapping UI with inputs disabled, plus a single clear CTA `Edit mapping` that transitions to Edit mode. No changes to mappings can be made from View mode.

AC3 – Explicit Edit mode and navigation  
- Edit mode for an integration is accessed only via explicit actions such as `Edit integration` (global button) or `Edit mapping` (from an entity’s read-only view); entering edit mode changes the URL (e.g. `/integrations/{integration}/edit`) and shows a visible `Edit mode` label.  
- In Edit mode, the layout uses a clear structure (e.g. stepper `Entities → Field mappings → Review` or left-nav) so the user understands where they are in the configuration flow.  
- Edit mode shows sticky primary actions (`Save` / `Cancel` or `Save & activate`) and an “Unsaved changes” indicator once configuration diverges from the persisted state; leaving the page without saving triggers a confirmation.

AC4 – Entities configuration in Edit mode  
- Configuring which entities are enabled for an integration is done via an explicit, accessible control such as a checkbox list or table—not via the current “bubbles” mechanism.  
- All entities that appear in View mode also appear in this Entities step, with synchronized statuses; enabling/disabling entities here immediately updates the summary on the page (but is not persisted until Save).  
- If disabling an entity would remove mappings that are currently in use, the UI surfaces a clear warning before the change is saved.

AC5 – Field mappings in Edit mode (per-entity focus)  
- When editing field mappings, only one entity’s mappings are visible at a time, navigable via tabs or a sidebar (e.g. `Support`, `Bugs`, `Feature Requests`); the user can switch entities without losing unsaved changes.  
- For each entity, the existing mapping UI is reused for the table of fields (source field, target field, required indicator, sync direction, etc.), with any necessary minor layout tweaks but no new mapping capabilities; the per-entity summary above the table surfaces only the count of mapped fields, not sync direction details.  
- Saving changes persists the updated mappings for all edited entities in one operation and returns the user to View mode where the entity summaries reflect the new configuration.

AC6 – New and partially configured integrations  
- For an integration with no entities configured, the View mode shows a clear empty state that explains what needs to be done and offers a single primary CTA `Set up integration` that goes to Edit mode.  
- For integrations with partially configured entities (e.g. entity enabled but required fields unmapped), View mode highlights these with a warning badge (e.g. `Needs attention`) and the Review step in Edit mode lists them explicitly before allowing activation.  
- After completing the flow and saving, a PM/IT user can confirm from View mode, in under 10 seconds, which entities are active for the integration and whether any need attention.

## NFRs / Constraints

- **NFR1 – No backend changes required**  
  - The redesigned pages consume the existing integration and mapping APIs; any additional data needed for summaries is derived from current structures without changing the persistent model.

- **NFR2 – Preserve mapping behavior**  
  - Field-mapping semantics (how mappings are applied, sync directions, scheduling) remain unchanged; only the UX around them is updated.

- **NFR3 – Learnability and safety**  
  - First-time users must be able to understand, from UI alone, whether they are in View vs Edit mode and whether unsaved changes exist.  
  - It should be impossible to accidentally change an integration’s configuration without (a) explicitly entering Edit mode and (b) clicking a Save / Save & activate action.

- **NFR4 – Performance**  
  - Loading the Integrations list and an individual integration detail page must remain within current acceptable performance envelopes (no perceptible regression compared to the existing UI).

- **NFR5 – Accessibility**  
  - All core controls in View and Edit modes (entity toggles, tabs, save/cancel) are keyboard-operable and support screen-reader labels for statuses like `Enabled`, `Needs attention`, and `Not configured`.

## Dev Tasks

1. **Design updated IA and flows for Integrations list and detail**  
   - Produce UX flows and wireframes for `/integrations`, integration detail View mode, and integration Edit mode, including entity list, mapping drawers, and the multi-step edit flow.

2. **Implement redesigned Integrations list page**  
   - Update the integrations index route to use new cards/rows, surfacing connection status, entity count, and last sync, and wire navigation into the existing per-integration routes.

3. **Implement integration detail View mode**  
   - Create or refactor the integration detail route to show full entity coverage and read-only mapping views using the existing mapping component with inputs disabled, plus explicit entry points into Edit mode.

4. **Implement Edit mode flow (Entities, Field mappings, Review)**  
   - Build the structured Edit mode experience with clear mode labeling, entity-selection controls (checkboxes/table), per-entity mapping tabs, change-tracking, unsaved-changes handling, and Save/Cancel actions wired to existing APIs.

5. **QA and polish**  
   - Verify View vs Edit separation, unsaved-changes prompts, and status accuracy across at least one fully configured integration (e.g. Monday) and one partially configured / empty integration; fix UX inconsistencies and edge cases.

---

## Test Strategy

1. **TS1 – Flow walkthroughs (PM / IT personas)**  
   - Manually test the end-to-end flows for: (a) reviewing an existing integration, (b) editing entities and mappings, and (c) setting up a new integration from scratch, ensuring mode boundaries and save semantics behave as per AC3–AC6.

2. **TS2 – Regression tests on mappings**  
   - For a sample integration (e.g. Monday with Support/Bugs/Feature Requests entities), capture current mapping behavior, then reconfigure the same mappings via the new UI and confirm that resulting data in Product OS and the Research Agent behavior is unchanged.

3. **TS3 – UX sanity checks**  
   - Run a short task-based test with at least one PM and one IT-like user to confirm they can, without guidance, answer: “Which entities are active for Monday?” and “How do I edit the Support Ticket mapping?” in under 2–3 minutes and without making accidental configuration changes.

4. **TS4 – Error and failure handling**  
   - Simulate API failures and slow loads for the integrations list, integration detail, and save operations to verify:
     - Errors show clear inline messages with a retry action and do not drop the user into Edit mode unintentionally.
     - Failed saves keep the user in Edit mode, preserve unsaved changes, and surface a clear error.
     - Using browser back/close during Edit mode either discards changes only after confirmation or returns to View mode with no partial saves.
